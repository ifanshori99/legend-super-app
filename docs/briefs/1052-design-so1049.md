## Temuan 1 (P1): clearance bukti lama berlaku lagi

Fakta (`payroll-payout-recon.service.ts`, `reconcileTrustedPayouts`, ~1830-1975):
1. tx1 membaca snapshot (operations, `facts.flagged`, ...) lalu commit.
2. Baca berkas bukti di luar transaksi (`fileOf`, `readShaOf`).
3. Observasi dicatat di tx2 per operasi. Pemulihan `ok` hanya diantrikan bila operasi itu ada di `evidenceFlagged`, dibangun dari snapshot tx1 yang basi. Fungsi `app.payout_recon_evidence_observe` (0663 ~100-125) membuang `ok` bila belum ada baris, dan tidak menyisipkan bila state+sha sama dengan baris terakhir.
4. Flag baru di tx3, flag lama di-raise ulang per chunk.

Celah: (A) run 1 snapshot tanpa flag; run 2 mencatat mismatch X dan clearance dua orang terjadi; berkas pulih dan run 1 membaca `ok` tetapi membuangnya (snapshot basi); berkas rusak X lagi -> observe melihat X = baris terakhir, tidak mencatat -> sidik sama -> clearance lama melepas slip. (B) urutan baca dan urutan catat bisa tertukar antar run (run 1 baca missing, run 2 baca ok, run 2 mencatat dulu, run 1 mencatat belakangan: `missing` basi menjadi terakhir).

Perbaikan:
- Keputusan `ok` ditentukan oleh keadaan DB saat observasi (di bawah kunci), BUKAN snapshot: panggil observe untuk `ok` pada setiap operasi yang punya `evidenceKey`; fungsi tetap membuang `ok` bila belum ada baris non-ok (jadi tidak ada tulis sia-sia).
- Serialkan baca berkas sampai pencatatan observasi per operasi: satu transaksi per operasi (withTenant), ambil advisory lock per operasi dengan KUNCI YANG SAMA dengan yang dipakai `payout_recon_evidence_observe` (periksa teks kunci di 0663; pg_advisory_xact_lock re-entrant dalam sesi yang sama), BACA berkas di dalam transaksi itu setelah kunci didapat, lalu observe. Urutan catat = urutan baca. Kunci hanya boleh diambil lewat panggilan SQL langsung dari service atau fungsi baru kecil di migrasi 0664 (EXECUTE legend_app, tanpa efek lain); pilih yang paling sederhana dan aman.
- Gagal baca selain NOT_FOUND tetap `error` (tidak dicatat, dicoba siklus berikut). Kegagalan observasi menggagalkan halaman (fail closed), seperti sekarang.
- Snapshot flag dipakai hanya untuk menentukan flag baru vs lama, bukan untuk observasi.
- Batas tenant: hanya operasi tenant sendiri; transaksi per operasi dibatasi dalam ukuran halaman yang sudah ada.

## Temuan 3 (P2): resolve item lain membuat flag baru untuk item yang sudah di-clear

Fakta (`readLostResolutions`, ~520-600): operasi untuk flag item yang attestation-nya hilang dipilih dari resolve terbaru per batch di `payroll_payout_approval_log` tanpa mengikat ke item. Resolve sah item B di batch yang sama menjadi "terbaru", operation id flag item A berubah, kunci flag baru, slip A tertahan lagi walau fakta A tidak berubah.

Perbaikan: ikat operasi ke item lewat jejak independen. `approval_log.grant_id` (UNIQUE, FK) -> `payroll_payout_grants` memuat `evidence_key`, `detail` (outcome), `kind='resolve'`, `batch_id`, `item_set_hash`; baris item memuat `resolution_evidence_key`, `resolution_outcome`, `updated_at`. Pilih operasi propose resolve yang grant-nya cocok dengan `resolution_evidence_key` dan `resolution_outcome` item (dan batch sama); bila beberapa cocok pilih yang paling baru yang `logged_at <= i.updated_at`. Bila tidak ada yang cocok: cadangan stabil = operasi propose resolve PALING AWAL di batch sejak cutover (bukan terbaru, supaya tidak bergeser oleh resolve lain), dan tetap flag (fail closed). Kunci flag item A harus tetap sama setelah resolve B. Tanpa migrasi bila cukup dengan query; 0664 hanya bila perlu.
