## Temuan

Tidak ada blocker P0/P1 yang ditemukan. Ada tiga temuan P2 berikut; urutan dimulai dari kasus yang memakai bentuk webhook yang sudah diuji suite.

- `apps/api/src/services/payment-webhook.service.ts:852` — **P2, invariant 8 / hasil provider hilang:** Jalur `payment_object` mengirim ID payment sebagai `providerRef` refund walaupun refund sudah menyimpan ID transaksi refund. Skenario: R `approved`, `amountIdr=100000`, `providerRef="rf_actual"` dari hasil pending; intent memakai payment `pay_actual`. Webhook terverifikasi dari integrasi asal membawa `{id:"pay_actual", reference:"<intentId>", status:"refunded", amount:100000}`. R menjadi kandidat tunggal, tetapi updater di `payment-refund.service.ts:2035` menolak `pay_actual !== rf_actual`; event permanen `ignored/REJECTED_CONFLICT` dan R tetap `approved`, juga bila R dikarantina. Fix: Untuk jalur ini pertahankan `refund.providerRef` yang sudah ada; gunakan ID payment sebagai fallback hanya bila belum ada referensi refund. Tambah kasus dengan referensi `rf_*`; test saat ini di `payment-doit-refund-webhook.test.ts:828` menyamakan referensi refund dengan ID payment sehingga celah terlewat.
- `apps/api/src/services/payment-webhook.service.ts:1135` — **P2, invariant 8 / hasil refund saat integrasi dinonaktifkan tidak tercatat:** Fallback autentikasi masih hanya mengenali `data.reference` melalui `mintingIntegrationSecret:241`. Skenario: DOIT sedang memproses refund R dari integrasi A, A dinonaktifkan dan cache dibersihkan, lalu A mengirim webhook bertanda tangan benar dengan `data={object:"refund", id:"rf_actual", idempotency_key:"refund:<R>", amount:100000}`. A tidak ada dalam daftar secret aktif; helper mengembalikan `null` sebelum mencari integrasi R karena `data.reference` tidak ada. Penerimaan berakhir 401 tanpa menyimpan hasil, termasuk hasil untuk refund karantina; worker tidak memiliki event untuk dicoba ulang. Fix: Untuk event refund cari integrasi asal dari refund key/provider refund ID atau `payment.reference` yang tervalidasi dan dibatasi tenant, lalu tetap verifikasi HMAC menggunakan secret integrasi tersebut sebelum menerima event.
- `apps/api/src/services/payment-doit-refund-webhook.ts:104` — **P2, invariant 8 / parsing objek refund menjadi objek payment:** Keberadaan string `reference` membuat fallback `paymentFacts(record)` berjalan meskipun `object === "refund"`. Skenario input: R `approved` dengan sumber payment `pay_actual`; webhook `refund.failed` terverifikasi membawa `{object:"refund", id:"rf_actual", idempotency_key:"refund:<R>", reference:"<intentId>", status:"failed", amount:100000}`. Parser membuat `facts.payment.id="rf_actual"`; `paymentMatchesRefund` membandingkannya dengan `pay_actual`, menandai event permanen `ignored/REFERENCE_MISMATCH`, dan R tetap `approved`, juga bila dikarantina. Fix: Jangan melakukan fallback `paymentFacts(record)` untuk objek bertipe refund; tetap izinkan `record.payment` eksplisit. Kasus ini kondisional pada tambahan field `reference`; belum ada bukti bahwa DOIT produksi mengirim bentuk tersebut.

## Batas bukti

Skenario temuan tambahan dibuktikan dengan fungsi asli dan stub, belum direproduksi sebagai tiga request end-to-end pada DB nyata. Suite integrasi yang ada lulus tetapi belum mencakup ketiga variasi tersebut. Tidak menjalankan build, suite penuh, atau transaksi DOIT nyata dalam review read-only ini.

[Dokumentasi refund DOIT](https://doit.id/docs/en/#refund) membolehkan refund parsial hingga jumlah pembayaran asal; [dokumentasi webhook](https://doit.id/docs/en/#webhooks) mencantumkan `refund.succeeded` dan `refund.failed`, tetapi belum menjelaskan bentuk `data` refund. Karena itu temuan parser ketiga memakai bentuk flat yang didukung kode ditambah `reference`, bukan klaim tentang payload produksi yang telah diamati. [Referensi error DOIT](https://doit.id/docs/en/#errors) juga dibaca sebagai konteks.
