# Sub-brief: top-up kas kecil kena batas + anti pecah (keputusan CTO 13 Nov 2026, tingkat K uang)

Basis: Q7 sudah ada (commit fdc8df999): `cash_bank_entries.status` pending_approval/approved/rejected, `approveCashBankEntry`/`rejectCashBankEntry` (accounting-cash-bank-entries.service.ts ~:665-766, `lockEntryForDecision`, CASH_OUT_SELF_APPROVAL, CASH_ENTRY_NOT_PENDING), batas `readLimitIdr(tx, tenantId)` :538 (default 5jt, perbandingan strict `>` di :424-426), izin approve `accounting.cash_bank.approve`. Brief Q7: docs/briefs/sub-cash-out-approval.md.

## Keputusan
1. Top-up kas kecil dari bank (`createPettyCashMovement` kind topup, accounting-petty-cash.service.ts:360, jurnal :416, idempotency :379, tanggal outlet :412) kena batas + persetujuan yang SAMA dengan kas keluar: jumlah > batas -> pending_approval, tanpa jurnal, tanpa mengubah saldo dana/petty_cash_entries sampai disetujui. Kind `return` (kas kecil -> bank) tidak kena.
2. Anti pecah: untuk pembuat yang sama (created_by) di outlet yang sama pada hari yang sama (hari bisnis menurut zona waktu outlet; `loadOutletClock` inventory-ops.shared.ts:157 + `businessDateOf` packages/shared/src/core/time.ts:188; dihitung dari waktu SERVER created_at, BUKAN entry_date yang bisa diisi mundur; outlet NULL -> kelompok tersendiri dengan zona Asia/Jakarta): bila jumlah entri ini + total kas keluar + top-up (yang belum ditolak: approved atau pending) milik pembuat itu di outlet itu hari itu > batas, entri INI masuk pending_approval (walau jumlahnya sendiri <= batas). Entri sebelumnya tidak diubah. Contoh gagal-dulu: batas 5jt, 3 x Rp2jt hari sama -> yang ke-3 pending (yang 1-2 langsung posting). Pembuat lain / outlet lain / hari lain tidak dijumlahkan. Entri ditolak tidak dihitung.
3. Serialkan pengajuan paralel per (tenant, pembuat, outlet): `pg_advisory_xact_lock(hashtextextended(...))` di dalam transaksi sebelum menjumlahkan, supaya 3 submit paralel tidak lolos semuanya.
4. Hindari hitung ganda: top-up pending yang kemudian disetujui menghasilkan baris petty_cash_entries (kind topup) -> jangan dihitung dua kali (pakai idempotency key berawalan `pt:` untuk menandai baris hasil persetujuan lalu kecualikan, atau cara setara).

## Desain (CTO, boleh disanggah dengan alasan)
- Top-up pending disimpan di `cash_bank_entries` sebagai kind baru `petty_topup` (bukan di petty_cash_entries, supaya pembaca saldo/ledger/jurnal-parked-retry petty tak tersentuh). Kolom: legal_entity_id, outlet_id (wajib), bank_account_id (sumber), amount_idr, description, created_by, status... `counter_account_id` NULL (akun kas kecil diturunkan dari pemetaan dana saat disetujui). Perlu migrasi 0498 (nomor berikut; journal.json idx 497 terakhir): ubah CHECK kind (cash_in, cash_out, transfer, petty_topup) dan cash_check/transfer_check yang relevan; CHECK status approved <=> journal_entry_id terisi tetap berlaku untuk petty_topup (disetujui = jurnal topup terposting; kalau periode tertutup, setujui GAGAL 4xx dan tetap pending, JANGAN parkir).
- Persetujuan petty_topup: `approveCashBankEntry` untuk kind petty_topup menjalankan topup nyata dalam transaksi yang sama (fungsi inti topup di petty service diekstrak agar dipakai bersama; idempotency key `pt:<entryId>`; saldo naik tepat sekali; entri petty_cash_entries; jurnal dikaitkan ke journal_entry_id). Setuju dua kali tidak menggandakan saldo/jurnal. Tolak: tidak ada saldo/jurnal. Pembuat tak boleh memutuskan (sama dengan Q7).
- Respons POST movement topup yang pending: HTTP 202, body `{ data: CashBankEntry }` (status pending_approval, kind petty_topup). Web (petty-cash-movement-dialog) menangani 202: toast "menunggu persetujuan", tutup dialog, entri tampil di daftar Kas & Bank dengan status.
- Helper bersama baru `apps/api/src/services/accounting-cash-limit.service.ts`: `readLimitIdr` (pindah/ekspor), `requiresApproval(tx, {tenantId, actorId, outletId, amountIdr, now})` memegang lock advisory + penjumlahan anti-pecah; dipakai createCashBankEntry (cash_out) dan createPettyCashMovement (topup).
- DTO/shared: kind `petty_topup` di CashBankEntry (banking.ts) + label web (status-badges/lib/i18n ws07 cash-bank); zod input movement tetap.

## Test gagal-dulu (uang)
(1) topup <= batas sendiri dan di bawah akumulasi: langsung (saldo naik, jurnal); (2) topup > batas: 202 pending, 0 jurnal, saldo dana tak berubah, 0 baris petty_cash_entries; (3) setujui: saldo naik tepat sekali, 1 jurnal, setuju dua kali (seq + paralel) tak menggandakan; (4) pembuat tak bisa setuju sendiri; tolak -> tak ada saldo/jurnal; (5) anti pecah: 3 x 2jt cash_out hari sama oleh pembuat sama outlet sama -> ke-3 pending, 1-2 langsung; campur 2jt cash_out + 2jt topup + 2jt cash_out -> ke-3 pending; (6) pembuat lain, outlet lain, hari lain (waktu outlet beda zona: dua entri melewati tengah malam lokal outlet tidak dijumlahkan) tidak dijumlahkan; entri ditolak tidak dihitung; (7) 3 submit paralel 2jt (Promise.all): tepat 2 langsung + 1 pending; (8) tenant lain ditolak; (9) entri hasil persetujuan topup tidak dihitung dobel pada anti-pecah; (10) test lama kas keluar/petty tetap hijau (amount kecil).
