## P1. legend-hxpd5 + legend-060xt (satu implementer, Opus; SQL yang sama)

Masalah hxpd5: `intentBackedAt` (`services/accounting-auto-journal-guards.ts:506`) menjumlah tender captured intent tanpa mengurangi bagian gateway yang diretur refund POS (`pos_order_refunds.lines`, jurnal `order.refunded` mengkredit `customer_deposit` sebesar bagian gateway). Contoh wajib di test: intent diterima 100k, jual POS QRIS 100k (tender intent itu, penjualan terposting), refund POS baris `qris` 30k (jurnal terposting), payout refund intent 30k completed → jurnal payout harus POSTED, bukan parkir `POSTING_AMOUNTS_MISMATCH`. Tambah kasus negatif: payout 30.001 (atau 31k) tetap parkir mismatch.

Masalah 060xt: `posSaleInUseOfIntent` (`services/payment-admin.service.ts:128`) mencari tender `authorized` lewat `payment_intent_id = intentId`. Tender QRIS menyimpan intent pertama link; refresh QR membuat intent B di link yang sama (`payment.service.ts` refreshIntent/createIntent) tanpa memperbarui tender; webhook paid baru rebind saat capture (`pos-order-payment.ts` ~:707). Skenario: tender authorized (intent A, link L, pesanan terbuka), intent B di link L paid, refund B penuh lolos, webhook capture B → tamu dibayar dua kali. Fix: tender `authorized` dicocokkan lewat `t.payment_link_id = <payment_link_id intent>` (tenant-scoped), di subquery pemilihan order DAN di filter `on_intent`; tender `captured` tetap lewat `payment_intent_id`. Test: tender authorized intent A, intent B paid di link sama, refund B → 409 `REFUND_INTENT_IN_POS_SALE`. Pola test: `src/test/payment-refund-pos-tender-guard.test.ts` (dibuat di 179).

Satu sumber kebenaran: buat modul baru `services/pos-intent-attribution.ts` yang mengekspor pembangun SQL atribusi (per order+metode: `on_intent`, `on_method`, `returned`, aturan CASE yang sekarang ada di `posSaleInUseOfIntent`: returned >= on_method → seluruh on_intent kembali; on_intent = on_method → least(returned, on_intent); selain itu 0, fail closed). Parameter: tenant, intent, mode tender (`held`: captured + authorized pesanan terbuka, cocok link untuk authorized, kecualikan pesanan dengan `pos_order_voids`; `ledger`: captured saja via `payment_intent_id` dengan filter waktu `salesAt(bound)`), dan filter waktu refund POS (ledger: refund POS dihitung bila `refunded_at <= waktu payout` untuk bound refund, `< saleAt` untuk bound sale; cek nama kolom di `db/schema/pos-order.ts:479`). `posSaleInUseOfIntent` dan `intentBackedAt` keduanya memakai modul itu; jangan salin rumus. `intentBackedAt.tenders` menjadi tender captured dikurangi bagian yang diretur yang teratribusi. Perhatikan `salesAt`/`saleAt` merujuk kolom drizzle tabel `orders` tanpa alias; SQL mentah harus konsisten dengan itu.
Pertanyaan yang wajib kamu jawab di laporan: apakah `intentBackedAt` (ledger) harus mengecualikan pesanan yang di-void (`pos_order_voids`)? Periksa jurnal void (`accounting-auto-journal-void.ts`) apakah mengkredit balik `customer_deposit`; bila ya dan `intentBackedAt` masih menghitung tendernya, payout setelah void juga parkir. Jangan perbaiki tanpa bukti; laporkan temuan + test bila jelas.
File: `services/pos-intent-attribution.ts` (baru), `services/payment-admin.service.ts` (hanya `posSaleInUseOfIntent`), `services/accounting-auto-journal-guards.ts` (hanya `intentBackedAt` + helper waktu refund POS), test `src/test/payment-refund-pos-tender-guard.test.ts` (060xt) dan test hxpd5 di `src/test/accounting-auto-journal.test.ts` (pola helper `makeWorld`, `seedPosOrder`, `deliver`, `post`, `parkedOf`, `journalCount`).
