## Bug

`refileRecoveryRefundAfterFailure` (`services/order-recovery-refund.ts` ~872) has a closure `settleFinalFailure` (~919) that stamps `order_issues.refund_rejected_at` and requests the journal reversal. The first filing (~636) recorded the goods payout on the promo ledger: `orderPromoPartialRefundPort.recordPartialRefundPayout` adds to `promotion_order_applications.refunded_paid_idr`, and `promoRecordedIdr` is stored in the first filing's `payment_admin_idempotency.response` (key `orderRecoveryRefundKey(issueId)` = `order-recovery-refund:<issueId>`). The refund then fails finally (`provider_declined`, `cap_exceeded`, `source_document`, `refile_limit`), the line is re-reported as a NEW issue, and the recompute (`crm-promo-refund.ts` ~690) computes `refundDueIdr` ~0 because `refunded_paid_idr` still includes the first payout -> `nothing_left` -> guest money stuck.

## Fix (decided)

1. Section A `crm-promo-refund.ts`: new exported function + port method `returnPartialRefundPayout(tx, context, { orderId, idempotencyKey, payoutIdr, at }): Promise<{ returnedIdr: number }>` on `PromoPartialRefundPort`.
   - `assertTrustedScopedContext`; validate orderId (orderIdSchema), payoutIdr safe int >= 0, idempotencyKey string 1..100.
   - `lockOrder(tx, tenantId, orderId)` first, then look up `promo_command_idempotency` (tenantId, key = idempotencyKey). Existing row: return its stored `{ returnedIdr }` (no change). Operation `"promo_payout.return"`, fingerprint = sha256 hex of JSON `[tenantId, operation, {orderId, payoutIdr}]`; same key different fingerprint -> return stored anyway? NO: throw 409 IDEMPOTENCY_KEY_REUSED (same as crm-promo-idempotency.ts).
   - Application row FOR UPDATE (tenant scoped). None -> returnedIdr 0. Released -> returnedIdr 0 (do NOT throw: the caller is a failure hook that must not roll back).
   - returnedIdr = min(payoutIdr, application.refundedPaidIdr); if > 0 update `refundedPaidIdr = refundedPaidIdr - returnedIdr` (tenant scoped).
   - Insert the idempotency row (response `{ returnedIdr }`) in all cases (incl. 0), so a replay never gives back twice.
   - If returnedIdr > 0, write an audit row `promo_application.payout_returned` (objectType `promo_application`, objectId orderId, actorType system, after: { orderId, returnedIdr, refundedPaidIdr: new value }) — make sure the audit safe-field list used includes those fields.
   - Wire it into `promoPartialRefundPort` and into `orderPromoPartialRefundPort` in `services/order-promo-refund.ts` (re-export the same function). Update any other object/fake typed `PromoPartialRefundPort` (grep: `services/pos-order-ports.ts`, `services/pos-order-corrections.ts`, tests `order-promo-db.test.ts`, `pos-refund-promo-db.test.ts`, `crm-promo-db.test.ts`) so typecheck stays green.

## Round 2 (architect review of dbe08344) — decided fixes

Findings: (1) returned payout goes to the order pool; another issue filed before the re-report absorbs it (kopi final-fail -> roti filed records kopi+roti -> roti rejected keeps all -> kopi re-report nothing_left). (2) re-report recompute has refundedNow=0 (refundedSubtotalIdr still counts the line) -> `order.refunded` gross=net, discount=0 (books wrong; `order-recovery-refund-amount.ts` promoParts ~188). (3) key `order-recovery-refund:<id>:promo-return` is a valid client Idempotency-Key in the shared `promo_command_idempotency` table -> attacker pre-claims -> hook throws 409 forever. (4) lock-order comments wrong: the hook takes intent -> issue -> promo.

Section D (src + tests, one implementer):

Update port type + doc.
