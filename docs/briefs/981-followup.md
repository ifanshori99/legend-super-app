## Butir

1. **Revoke tetap terbuka saat modul `mcp` mati.** `POST /api/ai/mcp/mcp-clients/:id/revoke` dan `POST /api/ai/mcp/mcp-tokens/:id/revoke` (file `apps/api/src/routes/ai-mcp-admin.routes.ts`, kini lewat `requireMcpModuleEnabled()` di `common`) harus bekerja saat modul mati, tetap dengan auth, origin tepercaya, dan izin yang sama (`mcp.client.manage` untuk klien; token: `own`). Rute lain (list, approve, preview, authorize, dll) tetap 404 `TENANT_NOT_FOUND` saat modul mati. Cek juga service `revokeMcpClient` / `revokeMcpToken` tidak menolak karena modul. Sejalan platform-lock: penghapusan kredensial tetap terbuka.
2. **Discovery/authorize/register tak bisa dibedakan dari tenant tak dikenal.** `apps/api/src/routes/mcp.routes.ts`: kini tenant bermodul mati mendapat 404 `TENANT_NOT_FOUND` sedangkan tenant tak dikenal mendapat 200 (discovery) atau jalur authorize/register-nya sendiri. Ubah: bila modul mati, perlakukan seolah `tenant` tidak ditemukan (`findTenantContext` null) sehingga status, header, dan body persis sama dengan tenant tak dikenal, untuk `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`, `GET /oauth/authorize`, dan `POST /oauth/register` (baris sekitar 134, 164, 189, 259). Penolakan tetap ditegakkan di bearer (`mcp-server.service.ts`), token exchange, dan eksekusi aksi: jangan diubah.
3. **Cek modul di token exchange pindah ke dalam transaksi terkunci.** `apps/api/src/services/mcp-oauth.service.ts` `exchangeAuthorizationCode`: cek `settings.moduleDisabled` kini di luar `withTenant`. Pindahkan ke dalam transaksi, sejajar `isAiPlatformLockedShared(tx, tenantId)` (setelah kunci bersama baris tenant, sebelum baris kode dibaca/dibakar) memakai `isMcpModuleDisabled(tx, tenantId)` dari `ai-platform-lock.ts`, sehingga tidak ada token/event tersisa dan kode tidak terbakar saat modul mati. Hasil ke pemanggil tetap `invalid_grant` "Invalid authorization code." (sama dengan kode tak dikenal). `loadMcpSettings` di luar transaksi tetap boleh untuk `mcpEnabled`.
4. **Migrasi data idempoten: beri flag `mcp` ke tenant yang sudah memakai MCP.** Migrasi `0546_*` (data saja, tanpa DDL): untuk tenant yang punya klien MCP aktif (`mcp_clients.status = 'approved'`; `pending` dan `revoked` tidak dihitung: klien yang belum disetujui belum memakai MCP, keputusan lebih ketat) atau token MCP aktif (belum dicabut, belum kedaluwarsa), tambahkan string `"mcp"` ke array `feature_flags.modules` (bentuk nyata `{modules: [...], integrationProviders: [...]}`, schema strict) tanpa menghapus/menggandakan isi lain; bila sudah ada, tidak diubah. Bisa dijalankan dua kali tanpa efek kedua. Journal idx 546 + snapshot `0546_snapshot.json` (salinan 0545 bila tanpa perubahan skema). Periksa bentuk `feature_flags` dan `MODULE_KEYS`/`isModuleEnabled` dulu. Tenant tanpa MCP tidak boleh tersentuh.
5. **TL-11 `scopeOutlets`: id outlet asing ditolak `forbidden`.** `apps/api/src/services/ai-tools/read-b/tl-11-anomalies.ts`: dengan jangkauan seluruh tenant (`reach.outletIds === null`) id outlet milik tenant lain kini lolos diam-diam dan menghasilkan data kosong. Ikuti pola TL-21 (`tl-21-review-summary.ts`, blok "known" count): bila `input.outletIds` diberikan, semua id harus outlet milik tenant ini, kalau tidak `forbidden()`. Boleh angkat pola itu menjadi helper di `read-b/support.ts` hanya bila TL-21 ikut memakainya tanpa mengubah perilakunya. Jangan ubah TL-07/08/20 (catat saja bila celahnya sama).
