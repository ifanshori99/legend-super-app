# Screenshots bead 945 (Duitku FE)

Generated by one script against the mock runtime (`VITE_API_MOCK=true`, own dev server on a free port). Sizes: desktop 1280x800, mobile 390x844 as a touch device (`hasTouch`, `isMobile`). Themes: light and dark for admin (`localStorage["legend-theme"]`); the guest pay dialog is light only (guest surfaces have no dark theme). Reduced motion is on.

Admin shots (`pembayaran-*`) show the `<main id="main-content">` column only (element screenshot, full width of the column, no sidebar or header). Except `loading`, the viewport is first grown (up to 4000 px) until main shows all its content, and the shot fails if main still scrolls inside. Duitku shots that show the form fail the run if the form, the Simpan button, the status panel or the test panel is not inside the shot. `loading` shots keep the normal viewport height.

Pay dialog shots (`bayar-tamu-dialog-*`): the bill is reloaded by URL (fresh query cache), the scenario is applied, the toast is dismissed, and only then the dialog opens (opening it starts the payment-options fetch). Each state waits for its own marker (skeleton, `[data-slot=error-state]`, VA reason text, a visible radio, open bank list, the empty-methods text with zero radios, the payFailed text, the pending CTA) and the shot fails, leaving no file, if it does not show up. Dialog shots are the viewport (desktop and mobile), taken with no toast on screen.

File name: `<screen>-<state>-<desktop|mobile>-<light|dark>.png`.

## States not reachable in the mock

- Duitku credentials with a successful connection test, and the active row ("Aktif" card): not capturable. The mock has no handler for `POST /api/org/integrations/:integrationId/test`, and the shared fixtures hold no Duitku row. The Aktifkan button stays disabled until a test stamps `lastCheckedAt` (`duitkuActivation`), and the mock store lives in the browser, so the script cannot seed a tested row. Only the saved-draft (not yet tested) state is shot. These need a mock handler for the test endpoint (a source change, out of scope here).
- Duitku `normal` and `empty` look the same: with no Duitku row in the fixtures, both show the empty form, status "Belum diatur".
- Pay dialog `no-methods` is not a built-in mock state: `?mock=empty` only empties the VA bank list and the `va-down` cookie only disables VA. The shot swaps the payment-options mock handler in page memory (see the table), so it shows the real empty-methods branch of `pay-dialog.tsx` but not a state a user can reach by a switch.
- Pay dialog `empty` (no_channels) and `va-down` (gateway_down) both show a disabled VA row; they differ only in the reason line. The script checks each reason text (`unavailableNoChannels` / `unavailableGatewayDown`). Dialog `loading` lasts 3 s, so the shot is taken about 0.3 s after the skeleton appears. The "masuk keranjang" toast is dismissed before the shot, so the toast itself is not shown.
- Pay dialog redirect hand-off (https `redirectUrl`, navigation to the payment screen): not captured; the mock never returns a gateway redirect URL. `sending` is shot before the call returns, `pay-failed` after a queued 500.
- Credentials form validation errors, save failure and secret-rotation confirmation: not captured.
- Admin loading state: the `slow` scenario is read in the browser runtime, so a server-rendered first paint may already show data or skeleton depending on timing. The shot is taken 0.7 s after DOM ready.
- Routing `error` and `empty`: shows whatever the screen renders for an empty or failing routing query; the error wait for routing is best effort (the script does not fail if no `[data-slot=error-state]` appears). Check the file before citing it as proof.
