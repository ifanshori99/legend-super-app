1. **P2 — Catch-up unfreeze dapat deadlock dengan worker pengikat bukti historis.** `apps/api/src/services/payroll-payout-dispute.service.ts:255` memanggil `recoverPayoutGlOfBatch` untuk batch saudara setelah SQL unfreeze sudah memegang kunci run dan batch target B (`apps/api/drizzle/0662_payout_freeze_run_lock.sql:278` serta `:282`). Pemulihan kemudian mengunci batch A melalui `apps/api/src/services/payroll-payout-gl.service.ts:1664`. Worker `bindHistoricalOperations` mengambil seluruh batch untuk satu key melalui `apps/api/src/services/payroll-payout-proof-backfill.service.ts:752`; helper pada `:379` langsung mengunci batch dalam urutan ID tanpa lebih dahulu mengunci run. **Skenario:** dua batch saudara A dan B berbagi payslip serta satu key bukti historis yang belum terikat, dengan ID A < B. Unfreeze B selesai menulis pembukaan tetapi belum masuk catch-up, sehingga memegang run+B. Worker mulai mengunci grup key tersebut, mendapat A, lalu menunggu B. Catch-up unfreeze memulihkan A lebih dahulu dan menunggu A: unfreeze menunggu worker, worker menunggu unfreeze. PostgreSQL membatalkan salah satu transaksi dengan `40P01`; bila unfreeze menjadi korban, seluruh pembukaan ikut rollback, sedangkan bila worker menjadi korban key dicatat `bind_failed` dan pemulihan tertunda. Pengurutan loop catch-up tidak menyelesaikannya karena B sudah dikunci sebelum loop. **Ketercapaian:** seleksi operasi historis pada `payroll-payout-proof-backfill.service.ts:906` dan `:933` tidak menyaring batch beku; backfill memang tetap diizinkan oleh aturan 0661 (`apps/api/drizzle/0661_payout_batch_freeze_guards.sql:22`). Contoh data yang memang didukung ialah item retur pra-0381 tanpa return claim pada A/B yang memakai `return_evidence_key` sama (`apps/api/drizzle/0641_payout_proof_global_gate.sql:43`); ini tidak melanggar unique key pada tabel return claim. Batch historis B dapat mempunyai log baru yang bisa disown sebelum key lama diproses: `recordPostingSource` menerima posting pending/skipped bersumber kosong (`apps/api/src/services/payroll-payout-source.service.ts:141` dan `:154`), dan `app.payout_posting_record_source` tidak memakai gerbang sejarah bukti serta menulis attestation melalui `apps/api/drizzle/0654_payout_trusted_steps_grant.sql:1364`. Attestation itu masuk log melalui versi 0659/0661. Jadi skenario tidak membutuhkan pembuatan pembayaran baru memakai key yang seharusnya ditolak. **Perbaikan:** worker mengambil seluruh kunci run terkait dalam urutan tetap sebelum mengunci batch; alternatifnya, pindahkan catch-up ke transaksi pemulihan tersendiri sesudah unfreeze commit, dengan mekanisme retry yang tahan kegagalan. **Usul test:** perluas fixture shared key historis serta test konkurensi backfill/unfreeze dengan dua batch saudara A < B, log sah B, dan grant password sah. Pasang barrier setelah SQL unfreeze B tetapi sebelum catch-up; mulai worker sampai A terkunci dan menunggu B, lalu lanjutkan catch-up. Setelah perbaikan, kedua transaksi harus selesai tanpa `40P01`, pembukaan tercatat tepat sekali, key terikat atau tercatat contested sesuai aturan, dan saldo/jurnal net serta fee tetap tepat tanpa pembayaran tambahan.
