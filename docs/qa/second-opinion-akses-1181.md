## Temuan

- **P1 — `apps/api/src/services/hris-offboarding.service.ts:747`: Hak mencabut peran tenant tetap memakai `canAssignRoles` dari sebelum kunci.** Sumbernya `routes/hris-offboarding.routes.ts:140–148`: snapshot HTTP menghasilkan boolean sebelum service menunggu advisory lock. Setelah kunci diperoleh, `loadHrisAccess` pada baris 688 memuat ulang akses HR, tetapi izin tambahan `access.role.assign` tidak dihitung ulang; `access.service.ts:1538–1545` hanya mempercayai boolean tadi. **Skenario:** HR memiliki dua assignment terpisah, yaitu `hr.employee.manage` tingkat tenant dan `access.role.assign` tingkat tenant. Request pencabutan akses karyawan yang memiliki peran tenant non-Owner sudah lolos snapshot lalu menunggu kunci. Owner mengakhiri assignment `access.role.assign` HR dan commit sebelum request diteruskan. HR tetap lolos pemeriksaan HR dan dapat mencabut peran tenant karyawan meskipun hak tersebut sudah dicabut. **Perbaikan:** Hitung ulang izin `access.role.assign` tingkat tenant di dalam transaksi setelah kunci, memakai aktor terverifikasi dan jam DB; jalur system tetap tanpa hak tambahan. **Usul test:** Dua koneksi dan penghalang advisory lock; pastikan request sudah mengantre, cabut hanya assignment pemberi `access.role.assign`, lalu lepaskan kunci. Harapkan `409 OFFBOARDING_ADMIN_ROLE`, assignment karyawan tidak berubah, sesi/push/shift tidak dicabut, status clearance tidak berubah, serta tidak ada event/audit keberhasilan.

- **P1 — `apps/api/src/services/platform-tenant-owner.service.ts:536`: Penunjukan/penggantian Owner tidak memeriksa ulang pencabutan Super Admin setelah menunggu kunci.** `authorize()` dipanggil pada baris 521–525; pemeriksaan registry pada baris 149 selesai sebelum `lockOwnerChanges()` pada baris 530. Pembacaan jam DB baru pada baris 536 digunakan untuk data Owner dan dukungan, tetapi tidak mengulang pemeriksaan registry. `platform-support.service.ts:141–149` mendefinisikan admin aktif sebagai baris `platform_admins` dengan `revoked_at IS NULL`; guard transaksi di `db/tenant.ts:68–69` hanya berlaku bila ada konteks mutasi dukungan, sehingga tidak menutup request platform biasa ini. **Skenario:** Super Admin lolos autentikasi, MFA, dan pemeriksaan registry lalu request menunggu kunci tenant. Registry admin tersebut dicabut dan commit selama penantian. Setelah kunci dilepas, request tetap dapat menunjuk akun kolaborator sebagai Owner permanen atau mengganti Owner lama. **Perbaikan:** Setelah kunci tenant, periksa ulang dan kunci baris registry aktif dalam transaksi sampai mutasi selesai; gunakan jam DB yang sama untuk pemeriksaan freshness MFA setelah penantian. **Usul test:** Dua koneksi; tahan kunci tenant, mulai request assign/replace dengan MFA sah dan tunggu sampai mengantre, set `platform_admins.revoked_at`, commit, lalu lepaskan kunci. Harapkan `403`, Owner lama tetap aktif, tidak ada assignment Owner baru, serta tidak ada event/audit/notifikasi keberhasilan. Audit penolakan boleh tetap tercatat.

## Area tanpa temuan konkret

- Audit outlet: `org.service.ts:983–1043` mengunci outlet, memperbarui status, dan menulis `outlet.status_changed` melalui `recordAudit(tx, ...)` dalam transaksi yang sama. Aktor HTTP berasal dari `requireAuth` melalui request context; atribusi dukungan diterapkan oleh penulis audit. Scope outlet dan RLS tenant tetap berlaku.
- Peran/jam DB: Tambahan kunci pada `updateCustomRole` mendahului kunci baris dan pemeriksaan izin. Jalur manager membaca ulang akses dengan jam DB setelah kunci terakhir. Helper sole-owner membaca jam DB setelah kunci tenant, membatasi assignment aktor yang sudah mulai, memakai akhir jendela eksklusif, dan menghitung calon Owner bertanggal masa depan secara membatasi. Tidak ditemukan bypass konkret jendela self-approval uang pada helper yang berubah.
- IP: Keempat limiter memakai `clientIpKey`; HTTP menggunakan alamat dari Express dan WebSocket produksi memakai resolver Express yang sama. Tidak ditemukan pembacaan header proxy mentah yang dapat menggeser bucket. Penyatuan IPv6 dalam `/64` mengikuti kontrak helper; IP di luar bucket normalisasi tersebut dipisahkan.
- Tablet bersama: Lima rute baru memakai rantai `sharedStaff` sebelum izin, lalu `actorOf(req)` untuk aktor layanan. PIN/token terikat sesi, perangkat, tenant, dan outlet; layanan membatasi tenant/outlet. Tidak ditemukan rute baru yang memakai hak pemilik cookie tanpa PIN kasir.
