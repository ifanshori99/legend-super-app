## Temuan

**Ringkasan: 2 P1, 2 P2; tidak ada temuan P0 atau P3 baru.**

- **P1 — Reversal membuat tagihan pinjaman dalam pesangon yang sudah dibekukan menjadi kurang.** `71b1155f7:apps/api/src/services/hris-offboarding.service.ts:1005` dan `:1023`; `apps/api/src/services/payroll-run-reversal.service.ts:712` (pada tip `001c996be`, panggilan ini di `:776`); `apps/api/src/services/hris-settlement.service.ts:309`. Completion hanya menahan reservasi run yang belum dikunci; run `locked` boleh mendahuluinya. **Skenario:** Pokok Rp1.000.000, run R mengunci cicilan Rp100.000 sehingga outstanding Rp900.000; offboarding diselesaikan dan snapshot membekukan Rp900.000. Tanpa payout, ekspor bank, atau run turunan, request dan approve reversal R tetap sah: `restoreLoanDeductions` mengembalikan outstanding menjadi Rp1.000.000, tetapi GET settlement selalu mengembalikan snapshot Rp900.000. Tagihan akhir kurang Rp100.000; simulasi setelah offboarding completed juga melewati pinjaman karyawan tersebut. **Perbaikan:** Tolak reversal yang mengubah saldo pinjaman dalam settlement completed, dengan pemeriksaan dan penguncian yang diselaraskan dengan completion; pembukaan ulang settlement harus melalui aturan eksplisit. **Usul test:** `Lock → complete offboarding → request/approve reversal`, urutan reversal sebelum completion, dan balapan completion vs reversal. Pastikan salah satu operasi ditolak atau snapshot tetap sama dengan saldo yang benar. Test `payroll-run-loans.test.ts:1879` saat ini hanya membalik run sebelum completion. Temuan tetap berlaku pada kedua tip pending.

- **P1 — Ledger koreksi lembur dapat ditandai reversed sementara pembayaran asal tetap berlaku.** `001c996be:apps/api/drizzle/0556_payroll_overtime_corrections.sql:46` (mirror `apps/api/src/db/schema/payroll-overtime-corrections.custom.sql:20`); `apps/api/src/services/payroll-overtime-correction.service.ts:552` dan `:654`. Cabang UPDATE trigger langsung menerima `settled → reversed` tanpa membaca atau mengunci status target run. Helper RLS memberi UPDATE kepada `legend_app` (`0001_tenant_rls.sql:49`); migrasi 0556 hanya mencabut DELETE/TRUNCATE (`:34`). **Skenario SQL dalam tenant sendiri:** Sumber S yang memenuhi batas aktivasi memiliki koreksi positif Rp100.000; target T sudah locked/paid dan membayarnya. `UPDATE payroll_overtime_corrections SET status='reversed', reversed_at=now() WHERE tenant_id=:tenant AND target_run_id=:T` diterima walaupun T tidak dibatalkan. Planner run U hanya menjumlah ledger `settled`, sehingga Rp100.000 ditawarkan dan dibayar lagi; primary key mencakup target run, sehingga U tidak berbenturan dengan T. Slip T tetap memuat pembayaran pertama. **Perbaikan:** Sebelum menerima UPDATE, kunci target run dan wajibkan status target benar-benar `reversed`; pertahankan larangan mengubah identitas/nominal ledger. **Usul test:** SQL langsung sebagai `legend_app` terhadap ledger T saat T locked dan paid harus ditolak; U tidak boleh membayar koreksi yang sama lagi. Reversal resmi T tetap harus membuka koreksi tepat sekali, dan total pembayaran koreksi aktif tidak melebihi Rp100.000. Ini celah pertahanan SQL, bukan jalur API yang ditemukan mengizinkan UPDATE tersebut.

- **P2 — Reversal run penagih piutang PPh21 memakai DELETE yang dilarang untuk role aplikasi.** `71b1155f7:apps/api/src/services/payroll-pph21-receivable-open-items.service.ts:409`, tetap sama pada `001c996be`; hak akses di `apps/api/drizzle/0058_invbe_rls.sql:32` dan mirror `accounting-ap-fa.custom.sql:36`. `undoRun` menghapus settlement, padahal tabel `accounting_open_item_settlements` append-only bagi `legend_app`; tidak ditemukan regrant atau fungsi berhak khusus untuk operasi ini. **Skenario:** Run Januari menimbulkan piutang Rp50.000, run Maret menagihnya dan masih locked, belum dibayar/diekspor serta tanpa run turunan. Request reversal Maret lolos; persetujuan menjalankan sinkronisasi open item lalu DELETE gagal dengan PostgreSQL `42501`, sehingga seluruh reversal rollback dan piutang tidak dapat dibuka kembali melalui alur tersebut. **Perbaikan:** Sediakan pembalikan settlement yang sesuai kontrak append-only, atau operasi SQL berhak khusus yang dibatasi tenant, jenis employee/PPh21, dan bukti reversal run; jangan memberikan DELETE umum ke ledger accounting. **Usul test:** Dengan role aplikasi produksi, `Raise Januari → collect Maret → reverse Maret` harus sukses tepat sekali, mengembalikan outstanding Rp50.000, kemudian reversal Januari harus sukses; ulangi sinkronisasi/reversal untuk membuktikan idempotensi. Test 972 saat ini mencakup collect/resync serta reversal raiser, tetapi tidak sukses reversal collector.

- **P2 — Perubahan principal melewati pembuktian saldo pinjaman terhadap ledger.** `71b1155f7:apps/api/drizzle/0461_payroll_loan_ledger.sql:45`, tetap sama pada `001c996be` (mirror `apps/api/src/db/schema/payroll-loan-ledger.custom.sql:43`). Trigger hanya memantau INSERT atau UPDATE `outstanding_idr,status`, sementara principal masih dapat di-UPDATE oleh `legend_app`; `payroll.custom.sql:46` hanya mencabut DELETE/TRUNCATE untuk `employee_loans`. **Skenario SQL dalam tenant sendiri:** Pinjaman disbursed dengan principal Rp1.000.000, outstanding Rp900.000, dan cicilan locked Rp100.000 menerima `UPDATE employee_loans SET principal_idr=999999 WHERE tenant_id=:tenant AND id=:loan`. CHECK nominal tetap lolos, trigger deferred tidak dijadwalkan, lalu commit menghasilkan `principal − outstanding = 99.999`, berbeda dari ledger Rp100.000. Reversal layanan normal sesudahnya ditolak karena saldo yang dipulihkan Rp1.000.000 melebihi principal baru. **Perbaikan:** Bekukan principal setelah pencairan atau cabut UPDATE kolom itu; masukkan perubahan principal dalam trigger pemeriksa ledger. **Usul test:** UPDATE principal langsung sebagai role aplikasi pada pinjaman disbursed/settled yang memiliki cicilan locked harus ditolak saat commit; saldo, principal, dan ledger harus tetap utuh. Temuan tetap berlaku pada kedua tip pending; tidak ditemukan jalur API normal untuk UPDATE principal tersebut.
