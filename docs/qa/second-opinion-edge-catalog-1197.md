## Temuan

- **R1 — P1 — `docs/deployment.md:413` (juga `apps/api/src/services/edge-catalog-sync.ts:199`): Rewind setelah restore tidak mengganti domain versi receipt link.** Skenario: Edge sudah menerima event kategori versi `1000`; cloud dipulihkan sehingga horizon menjadi `200`, lalu katalog di-restamp pada txid `200` dan watermark edge dikosongkan sesuai runbook. `resetCatalogSyncTxid` sengaja mempertahankan row dengan receipt link (`apps/api/src/services/edge-catalog-apply.ts:540`, `:566`, `:581`); `filterCatalogRecordsAfterEvents` membuang record dengan versi <= receipt `1000` (`:535`). Pull tetap menyimpan checkpoint dan waktu sukses (`apps/api/src/edge/catalog-puller.ts:839`, `:851`), sehingga nilai katalog edge tetap dari sejarah lama dan perubahan berikutnya `201..1000` ikut terlewat. Jalur link juga memakai `record.syncTxid` sebagai sequence (`apps/api/src/services/edge-master-data-publisher.ts:155`) dan MAX receipt lama (`apps/api/src/edge/db-link-store.ts:119`), sehingga bukan jalur pemulihan alternatif. Usul: Pakai generasi sejarah cloud pada seluruh penjaga versi katalog, atau sediakan prosedur pemulihan terkoordinasi yang aman untuk seluruh versi/receipt katalog; menghapus watermark saja tidak cukup. Pertahankan perlindungan terhadap replay HTTP lama dalam operasi normal. **Usul test T1 di bawah.**
- **R2 — P2 — `docs/deployment.md:413`: Full replay tidak menonaktifkan row yang hilang akibat restore.** Skenario: Item dibuat setelah backup dan sudah tersalin ke edge; restore menghilangkan item itu dari cloud tanpa menghasilkan tombstone. Runbook hanya mengosongkan checkpoint; reset stamp tidak menghapus/menonaktifkan row (`apps/api/src/services/edge-catalog-apply.ts:581`), dan pull hanya menerapkan record yang dikirim (`apps/api/src/edge/catalog-puller.ts:795`, `:801`). Setelah replay selesai, stream dianggap segar tetapi item lokal yang sudah tidak ada di katalog otoritatif tetap aktif. Ini dapat terjadi pada salinan HTTP tanpa receipt, sehingga terpisah dari R1. Usul: Tambahkan rekonsiliasi keanggotaan snapshot yang konsisten saat recovery, atau prosedur recovery yang menonaktifkan katalog lokal yang tidak lagi ada di cloud; jangan menyimpulkan ketidakhadiran dari satu halaman incremental. **Usul test T2 di bawah.**
- **R3 — P2 — `apps/api/src/services/edge-sync-conflict-alert.ts:343` (juga `apps/api/src/edge/runtime.ts:289`): Deduplikasi episode berubah menjadi deduplikasi seluruh set, sehingga restart memunculkan alarm ulang tanpa episode baru.** Skenario: Heartbeat `{A@t,B@t}` mengirim satu alert; cloud restart, A pulih, lalu heartbeat `{B@t}` dikirim. Cache per-entry kosong, sementara ID durable untuk `{B@t}` berbeda dari ID `{A@t,B@t}`, jadi penerima mendapat alarm kedua untuk episode B yang sama. Sebelum diff, ID per-stream B sudah menahan pengulangan ini. `catalogStaleAlerted.clear()` pada 1000 entry (`apps/api/src/edge/runtime.ts:303`) dapat memicu hal yang sama tanpa restart. Usul: Simpan deduplikasi episode per-stream secara durable, lalu gabungkan episode yang benar-benar baru menjadi satu notifikasi per heartbeat secara atomik. **Usul test T3 di bawah.**

R1 dan R2 menilai kelengkapan jalur restore/runbook yang baru ditambahkan. Helper reset/filter yang dirujuk memang sudah ada; masalahnya adalah mengandalkannya sebagai pemulihan sejarah database yang berbeda tanpa langkah tambahan.

## Usul test terarah

1. **T1 — Receipt lama + restore + perubahan baru:** Perluas `apps/api/src/test/edge-catalog-epoch.test.ts` dengan event katalog yang benar-benar diterapkan melalui link pada versi `1000`, bukan hanya seeding row melalui HTTP. Turunkan horizon ke `200`, restamp row ke versi `200`, jalankan recovery dan pull; pastikan nilai cloud diterapkan sebelum freshness dinyatakan sukses. Lalu kirim perubahan versi `201` lewat HTTP dan link; pastikan keduanya tidak hilang. Ulangi dengan receipt tombstone printer, serta pastikan HTTP lama dalam generasi yang sama tetap tidak dapat menimpa event lebih baru. Test saat ini melakukan seed lewat HTTP (`:425`, `:432`) sehingga tidak mencakup receipt tersebut.
2. **T2 — Row tidak ada dalam backup:** Sinkronkan item aktif hanya ke edge, restore cloud ke backup sebelum item dibuat, lalu ikuti recovery lengkap. Pastikan item tidak lagi tersedia untuk transaksi setelah stream dianggap segar; sertakan snapshot multipage dan update yang berjalan bersamaan agar rekonsiliasi tidak menghapus item valid. Verifikasi data tenant/outlet lain tetap utuh.
3. **T3 — Restart bersamaan dengan subset:** Di `apps/api/src/test/edge-catalog-stale-coalesce.test.ts`, kirim `{A@t,B@t}`, restart modul/runtime cloud, lalu kirim `{B@t}` sebagai heartbeat pertama; jumlah notifikasi per penerima harus tetap satu. `{B@t,C@u}` menambah tepat satu; subset/reorder berikutnya tidak menambah. Ulangi sesudah eviction cache dan dengan dua proses cloud. Test baru memeriksa subset sebelum restart (`:294`) dan set yang sama sesudah restart (`:311`), sehingga melewatkan kombinasi ini.

## Pemeriksaan fokus lain dan batas bukti

- **Marker/proxy/klien:** Tidak ditemukan jalur klien memalsukan response marker melalui request header. Route memasang marker hanya pada error cursor setelah autentikasi; edge mensyaratkan status 400 dan token persis, serta menolak redirect. Token bukan autentikasi respons tersendiri: TLS dan reverse proxy tetap bagian dari batas kepercayaan. Proxy yang sudah menguasai respons dapat memalsukan atau menghapus marker; tidak ada konfigurasi proxy production yang diuji dalam review ini.
- **Kompatibilitas cursor:** Edge baru dengan cloud lama tanpa marker sengaja tidak rewind pada 400. Probe sukses juga dibuang (`apps/api/src/edge/catalog-puller.ts:707`); cursor cat2 yang benar-benar ditolak cloud lama, atau marker yang dibuang proxy, tidak pulih otomatis. Perilaku ini sesuai aturan brief, dicatat sebagai batas kompatibilitas, bukan temuan tambahan. Tambahkan smoke test pasangan versi nyata dan forwarding marker di proxy deployment.
- **Heartbeat/1008:** Unknown field tingkat heartbeat dibuang, field yang dipakai tetap divalidasi. Hold `catalogStale` hanya aktif untuk close 1008 dengan alasan `Invalid frame` dalam jendela 10 detik, kemudian probe kembali setelah satu jam. Tidak ditemukan regresi konkret lain pada alur ini dari pemeriksaan statis; interaksi versi production belum diuji.
- **Notifikasi dan isolasi:** Tidak ditemukan kehilangan notifikasi atau kebocoran tenant/outlet baru pada diff. Scope berasal dari identitas node terautentikasi; transaksi notifikasi yang gagal tidak mengisi cache. Temuan R3 menyangkut alarm ulang. Ini bukan klaim bahwa seluruh mekanisme notifikasi sudah diuji.
- **Wraparound:** Stamp katalog dan horizon memakai `xid8`, termasuk epoch; pembanding baru memakai `BigInt`, sehingga wraparound xid 32-bit biasa bukan bukti false rewind. Jenis dan representasinya diperiksa melalui Context7 terhadap [fungsi snapshot PostgreSQL 17](https://www.postgresql.org/docs/17/functions-info.html) dan [transaction identifiers PostgreSQL 17](https://www.postgresql.org/docs/17/transaction-id.html). Tidak menjalankan simulasi wraparound database.
