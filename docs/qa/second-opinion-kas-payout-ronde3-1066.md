- **P1 — Pemanggil biasa dapat melepas hold bukti error tanpa pembacaan recon.** Rantai B, `apps/api/drizzle/0674_payout_qh11l_read_error_hold.sql:159`: wrapper `app.payout_recon_evidence_observe` hanya menolak `ok`, tetapi menerima `mismatch` identik atau `missing` yang mengembalikan fingerprint clearance lama. Skenario: recon mencatat mismatch A pada seq 10, dua orang memberi clearance, lalu storage error menghasilkan seq 11 dan slip tertahan. Pemanggil `legend_app` biasa memanggil `observe(tenant, operation, 'mismatch', hash_A)` tanpa membaca storage. Observasi seq 12 mempertahankan episode lama; pencarian awal run pada `:229` mengabaikan error sehingga kembali memakai seq 10, sementara `:249` menghapus `read_error` karena baris terakhir bukan error. Fingerprint kembali persis semula dan guard `apps/api/drizzle/0464_payout_990_flag_fingerprint.sql:365` melepas slip lewat clearance lama. Ini tidak membutuhkan `SET ROLE`, `ok`, atau grant recon, sehingga berbeda dari pengecualian login API/worker bersama. **Perbaikan:** Pembatalan hold error melalui seluruh hasil baca, termasuk `missing` dan `mismatch`, harus membutuhkan jalur recon tepercaya; wrapper biasa harus tetap mempertahankan hold tersebut. **Usul test:** Dari fixture `heldByError()` pada `apps/api/src/test/payroll-payout-1057-clearance-stale-evidence.test.ts:1466`, panggil `observeOwn(operationId, 'mismatch', sha256(BYTES_A))` tanpa pembacaan storage atau `recordReadOk`; slip harus tetap tertahan. Ulangi pola `missing → clearance → error → missing`. Test wrapper pada `:1540` hanya memakai SHA berbeda, sehingga tidak mencakup pengulangan A identik setelah error.
- **P1 — Return kas parked belum dicadangkan, sehingga persetujuan tunai dapat membelanjakan uang yang sudah dikembalikan.** Rantai A, `apps/api/src/services/accounting-petty-cash.service.ts:490`: `pendingPettyCashCreditsIdr` tidak menghitung `petty_cash_entries` jenis `return` dengan jurnal `parked`, padahal fund sudah berkurang; retry pada `:1472` kemudian mem-posting kredit 1102 tanpa pemeriksaan cakupan baru. Skenario tanpa menghapus mapping: entitas baru belum memiliki mapping `petty_cash`; top-up Rp1.000 parked membuat fund Rp1.000, lalu return Rp500 parked menyisakan fund Rp500. Tambahkan mapping dan post ulang top-up saja: GL 1102 menjadi Rp1.000. Approval batch gaji tunai Rp600 lolos karena `availableCash1102` masih membaca Rp1.000. Post ulang return mengurangi GL menjadi Rp500; handover Rp600 lalu membuat GL minus Rp100. Semua langkah dapat berurutan dan selesai sebelum kedaluwarsa approval, sehingga ini bukan race batas 24 jam atau penghapusan mapping yang dikecualikan. **Perbaikan:** Cadangkan return parked yang belum dijurnal dalam saldo tersedia, dengan identitas transaksi yang memastikan nilainya berhenti dihitung setelah jurnal terbit. **Usul test:** Jalankan urutan di atas melalui service/API; approval Rp600 harus ditolak dengan saldo tersedia Rp500, pembayaran Rp500 harus aman sebelum maupun sesudah retry return, dan pengulangan posting tidak boleh menghasilkan jurnal kedua. Cakup pula kas keluar/transfer dari rekening GL 1102 yang memakai guard saldo sama.
- **P2 — Deadlock jalur payroll.locked dari ronde 2 masih terbuka.** Rantai A, `apps/api/src/services/payroll-gl-consumer.ts:329`: jurnal `payroll.locked` masih diposting sebelum resolver pada `:354` mengambil entity lock melalui `apps/api/src/services/payroll-payout-gl.service.ts:934`. Jurnal locked normal tidak mengkredit `petty_cash`, sehingga backstop `accounting-journal.service.ts:536` tidak mengambil entity lock sebelum gerbang periode. Skenario: run memiliki minimal satu batch dan periode target belum ada; consumer menyisipkan periode melalui `accounting-period.service.ts:160`, lalu tertahan pada barrier. Return mengambil entity lock dan menunggu penyisipan periode yang sama; consumer melanjutkan resolver dan menunggu entity lock milik return. Siklus ini menghasilkan `40P01` dan membatalkan salah satu transaksi. Jalur consumer payroll tidak melalui `wouldPostingBeBlockedByClosedPeriod` yang sudah diperbaiki; consumer auto-journal mengabaikan event `payroll.locked`. **Perbaikan:** Ambil entity lock setelah run lock dan sebelum mem-posting jurnal locked, selaras dengan urutan run → entity → periode/jurnal. **Usul test:** Tambahkan kasus `payroll.locked` pada test lock-order 1053 dengan barrier setelah insert periode baru dan return paralel; keduanya harus selesai tanpa `40P01` serta tanpa jurnal ganda.
