Tanggal: 14 November 2026. Pemeriksaan read-only kode aplikasi; hanya laporan ini ditambahkan.

Rentang yang diperiksa: `origin/milestone/m1...origin/ui/panic-copy-subnav`, termasuk API panic yang dipanggil UI dan jalur notifikasinya. Snapshot referensi saat pemeriksaan:

- Basis: `9b8433f691f1d34533e9728ddf49f697112e174b`.
- Target akhir: `2c60a4bc8b919512326a9b6b21ec6c450c0618e0`. Saat pemeriksaan dimulai ref menunjuk `8473d310b10a57a214b4c175bd9bdd89e1e19988`; commit susulan hanya mengubah screenshot dan hasil axe. Diff pada `apps/api/src`, `apps/web/src`, serta `packages/shared/src` kosong di antara kedua SHA tersebut; bukti kode dan nomor baris tetap berlaku.
- Semua lokasi `berkas:baris` di bawah menunjuk **snapshot target**, dibaca melalui `git show`; HEAD worktree laporan berbeda dari target.

Hasil: **4 P1, 1 P2; tidak ada P0 atau P3**. Temuan 1–4 adalah celah pada integrasi fitur yang ditinjau; sebagian dependensi yang belum tersambung sudah ada sebelum diff. Temuan 5 adalah bug API bawaan sebelum diff, yang relevan karena frame baru juga membawa nama penanggap.

## Temuan

1. **P1 — `apps/web/src/features/facility-staff/components/panic-alert-layer.tsx:910`: alur PIN pemulihan tidak membuat sesi darurat, sehingga petugas tidak dapat mulai menerima alarm.** Skenario: perangkat terdaftar, petugas aktif sedang bertugas dan punya izin menerima alarm, tetapi browser belum mempunyai cookie `legend_emergency`. WS serta GET open-alerts ditolak; tautan pemulihan mengarah ke `/pos/ganti-pengguna`, yang membuat sesi POS melalui `/api/staff-pins/pos-session` (`apps/web/src/features/ws01-device-pin/api.ts:29`). Handler POS hanya menerbitkan acting-staff token (`apps/api/src/routes/pos-acting-staff.routes.ts:58`), sedangkan cookie darurat hanya diterbitkan jalur `POST /api/emergency/sessions` (`apps/api/src/routes/emergency.routes.ts:64` dan `:69`). Tidak ditemukan pemanggilan pembukaan sesi darurat di `apps/web/src`; PIN POS tidak menyelesaikan kegagalan penerima. **Usul:** hubungkan UI PIN dengan pembukaan sesi penerima darurat, lalu mulai ulang koneksi setelah berhasil. **Usul test:** E2E nonmock dengan perangkat dan petugas valid serta cookie darurat kosong; lakukan login PIN melalui UI, pastikan endpoint sesi darurat dipanggil dan cookie diterbitkan, kemudian tekan tombol dan buktikan tepat satu alert tampil serta dapat diakui.

2. **P1 — `apps/web/src/routes/_ops/fasilitas.tsx:26`: gate layer menyaring OM/GM yang sebenarnya berwenang menerima alarm.** Skenario: OM atau GM dengan template izin bawaan sedang bertugas, bahkan sudah mempunyai receiver session valid, membuka papan `/fasilitas`. Layout memasang `PanicAlertLayer` hanya untuk `facility.access.assist`; template `general_manager` dan `outlet_manager` punya `facility.booth.operate`, `facility.emergency.respond`, serta `facility.emergency.resolve`, tetapi tidak punya `facility.access.assist` (`packages/shared/src/access/roles.ts:209` dan `:294`). Mereka dapat membuka papan (`apps/web/src/routes/_ops/fasilitas.index.tsx:22`), tetapi layer dan socket tidak pernah dibuat. Guard memakai `permissions.includes` tanpa bypass manajer (`apps/web/src/lib/areas/guard.ts:24`). **Usul:** dasarkan pemasangan penerima pada `facility.emergency.respond`, dengan pemeriksaan outlet dan status bertugas tetap di API. **Usul test:** render layout menggunakan izin template OM dan GM serta sesi darurat valid; kirim frame panic, pastikan dialog tampil. Sertakan peran tanpa izin respond sebagai kontrol negatif.

3. **P1 — `apps/api/src/worker/notification-adapters.ts:705`: fallback notifikasi panic tidak dapat mengirim web push melalui factory produksi.** Skenario: petugas aktif sedang bertugas dan mempunyai subscription push, tetapi layar fasilitas/WS sedang tertutup. Event edge berhasil tersinkron dan rule baru membuat notifikasi kategori `emergency`; kategori ini secara bawaan hanya memakai `web_push` (`packages/shared/src/notification/schemas.ts:130`). Namun factory produksi menetapkan `channels.push = false` (`notification-adapters.ts:1465`), delivery lookup memaksa `hasPushSubscription: false` serta endpoint null (`:1207`, `:1220`), konfigurasi provider hanya menerima `disabled` (`:1413`), dan provider pengirim tetap disabled (`:1490`). Consumer dapat menyimpan attempt berstatus skipped dan melanjutkan event tanpa membangunkan ponsel (`apps/api/src/services/notification-consumer.ts:85`). **Usul:** sambungkan subscription lookup dan provider push nyata pada factory produksi sebelum mengandalkan fitur ini sebagai fallback. **Usul test:** jalankan event panic melalui `createWorkerNotificationHandlers` dan consumer/delivery yang dipakai produksi, dengan provider transport terkendali; buktikan subscription valid menghasilkan satu send yang diterima, bukan sekadar menguji resolver dengan `channels.push=true` buatan test. Uji juga kondisi provider tidak tersedia agar kegagalan terlihat oleh operator.

4. **P1 — `apps/api/src/services/panic-relay.service.ts:405`: press cloud-only tidak masuk antrean notifikasi sama sekali.** Skenario: outlet tanpa edge aktif menerima press langsung di cloud, sementara tidak ada WS penerima. Alert tersimpan dan respons press berhasil, tetapi jalur pembuatan hanya memanggil `queuePanicAlertEvent`; helper langsung kembali tanpa membuat event ketika proses bukan edge (`apps/api/src/services/panic-alert-outbox.ts:122`). Enqueue tujuan `notification` yang baru ditambahkan hanya berjalan pada penerapan event edge di cloud (`apps/api/src/edge/panic-alert-applier.ts:293`); press cloud-only tidak melewati applier tersebut. Jadi memperbaiki provider push saja tidak memperbaiki kasus ini. **Usul:** enqueue notifikasi secara atomik pada pembuatan pertama alert cloud-only, dengan dedupe yang sama seperti jalur edge. **Usul test:** POST press pada mode cloud untuk outlet tanpa edge aktif; pastikan tepat satu event tujuan notification dan satu notifikasi per penerima. Replay eventId yang sama serta press lain yang dilipat ke alert terbuka tidak boleh menambah notifikasi atau biaya kirim.

5. **P2 — `apps/api/src/services/panic-receiver-session.ts:352`: pemeriksaan ulang socket tidak membaca pencabutan sesi tersimpan; race upgrade dapat mempertahankan akses ke lokasi dan nama setelah logout/penggantian sesi.** Ini bug bawaan sebelum diff. Skenario konkret: upgrade sudah membaca sesi yang masih valid lewat `findReceiverSessionAny` (`:369`), lalu logout atau penggantian sesi menyimpan `revokedAt` dan mengumumkan pencabutan sebelum upgrade mendaftarkan subscriber (`apps/api/src/edge/panic-relay-realtime.ts:133` dan `:158`). Pengumuman tidak menemukan socket tersebut. Setelah upgrade selesai, `recheckReceiverSession` hanya mengevaluasi kondisi akun/PIN/perangkat/izin/duty dari objek sesi lama; ia tidak membaca lagi `panic_receiver_sessions.revoked_at`, sehingga pemeriksaan setiap send tetap lolos selama kondisi lain valid. Socket lama dapat terus menerima lokasi alert dan frame baru `acknowledged.byName` (`apps/api/src/services/panic-relay.service.ts:1246`). **Usul:** baca status sesi tersimpan saat recheck dan pastikan pencabutan yang beradu dengan subscribe tidak terlewat. **Usul test:** gunakan barrier sesudah pembacaan sesi dalam autentikasi; cabut sesi, lanjutkan upgrade, lalu buat panic dan acknowledgement. Pastikan tidak ada frame lokasi/nama dan koneksi ditutup 4401. Tambahkan pemeriksaan langsung: simpan objek `ReceiverSession`, cabut sesi di DB, lalu `recheckReceiverSession` harus gagal.

## Batas akses dan duplikasi yang diperiksa

- Tidak ditemukan skenario konkret petugas outlet lain membaca atau mengakui alert lewat endpoint yang ditinjau: query open-alerts, ACK yang mengunci row, join lokasi, serta audience hub memakai identitas tenant/outlet yang eksplisit. Tidak ditemukan bypass klaim "menuju lokasi" lintas outlet dalam pemeriksaan ini.
- Tidak ditemukan skenario konkret satu replay menimbulkan biaya kirim ganda: ingest memakai advisory lock per perangkat, identitas event serta folding; applier enqueue hanya setelah insert pertama; consumer memakai unique source event/dedupe dan `onConflictDoNothing`. Frame WS ulang memang dimungkinkan untuk pemulihan, tetapi klien melakukan dedupe; pengiriman ulang frame bukan bukti biaya provider ganda.
- Kesimpulan di atas berasal dari penelusuran statik, bukan pembuktian runtime bahwa seluruh kondisi akses atau race sudah aman.
