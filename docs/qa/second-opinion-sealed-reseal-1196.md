# Second opinion 1196 — reseal kolom tersegel beku

Review statis selesai: **1 P1, 3 P2; tidak ada temuan P0 atau P3**. P1 memperluas cakupan risiko yang sudah diterima CTO: kompromi API dengan akses SQL dapat merusak envelope beku tenant lain, bukan hanya tenant sendiri. Tidak ditemukan bypass dari permintaan HTTP biasa dalam diff ini.

## Temuan

- **P1 — `apps/api/drizzle/0720_sealed_reseal_frozen.sql:66` (grant pada `:39`): Batas risiko “tenant sendiri” tidak ditegakkan terhadap API yang terkompromi.** Skenario: login API menyetel `app.tenant_id` ke tenant B dan `app.outlet_ids='*'`, membaca ciphertext B, lalu `SET LOCAL ROLE legend_sealed_reseal` dan memanggil fungsi dengan tenant B serta envelope sampah sepanjang sama dan versi tidak turun; CAS dan pemeriksaan GUC lolos. Policy lama memang mempercayai GUC (`0001_tenant_rls.sql:22`, `:48`; `0032_outlet_rls.sql:20`, `:86`), tetapi hak baru kini membuka penulisan baris beku B, termasuk kode voucher aktif. Ini bukan klaim bypass RLS baru pada operasi biasa; ini koreksi batas kerusakan dari capability baru di bawah ancaman yang disebut brief. **Perbaikan:** Cabut membership reseal dari `legend_app`, berikan hanya ke login data khusus proses rotasi dengan kredensial yang tidak tersedia bagi proses API, dan sesuaikan provisioning/audit. Login queue `WORKER_DATABASE_URL` yang ada bukan pengganti langsung karena memang dipisahkan dari akses tabel aplikasi. **Usul test:** Gunakan login API nyata, ganti GUC ke tenant B, dan pastikan upaya SET ROLE/EXECUTE ditolak; login rotasi tetap berhasil melakukan reseal B tanpa mengubah plaintext atau kolom lain. Test mismatch GUC yang ada belum menguji skenario ini.
- **P2 — `apps/api/src/db/provision-roles.ts:1109`: Audit capability grup melewatkan privilese berbahaya yang tidak diwarisi login.** Skenario drift: admin memberi `GRANT SELECT ON pg_catalog.pg_authid TO legend_sealed_reseal`; audit baru mengecualikan katalog sistem, sedangkan audit umum memeriksa hak efektif login, yang tidak mewarisi grup ini. Audit dapat lolos, tetapi aplikasi kemudian SET ROLE dan membaca hash autentikasi seluruh login. Pengecualian `pg_catalog` pada `:1121` juga melewatkan grant EXECUTE builtin sensitif; daftar hak tabel pada `:1112` tidak memuat `MAINTAIN` pada PostgreSQL 17+, walaupun helper umum di `:507` sudah mendukungnya. **Perbaikan:** Audit hak efektif grup secara langsung memakai pemeriksaan sensitive/builtin, tabel dengan baseline PUBLIC, sequence, dan DDL yang sudah tersedia; larang MAINTAIN secara kondisional pada PG17+. **Usul test:** Injeksi grant SELECT `pg_authid`, EXECUTE builtin non-PUBLIC, dan MAINTAIN secara terpisah; audit harus menolak masing-masing lalu kembali lolos setelah REVOKE. Grant berbahaya ini tidak dibuat migrasi normal; temuannya adalah celah deteksi drift.
- **P2 — `apps/api/src/worker/sealed-secret-reseal.job.ts:693`: Satu baris beku terkunci dapat menghentikan seluruh sweep.** Skenario: transaksi lain menahan `SELECT ... FOR UPDATE` pada final order; SELECT tanpa lock pada pass beku tetap mendapatkan baris itu, lalu UPDATE dalam fungsi menunggu pelepasan lock tanpa batas lokal. Pool, `withTenant`, dan fungsi tidak menetapkan `lock_timeout`/`statement_timeout`; AbortSignal baru diperiksa di antara batch (`:735`), sehingga kolom/tenant berikut tidak diproses selama menunggu. `idle_in_transaction_session_timeout` pada login job tidak membatasi query yang sedang aktif menunggu lock. **Perbaikan murah:** Tetapkan `lock_timeout` singkat di savepoint per baris, biarkan rollback mengembalikan role/setting ketika timeout, hitung failed, dan lanjutkan; baris terkunci wajib tetap masuk remaining. **Usul test:** Kunci satu baris lewat koneksi kedua, jalankan job dengan batas singkat, pastikan baris bebas tetap dipindah dan remaining masih 1; lepaskan lock lalu rerun sampai remaining 0.
- **P2 — `apps/api/drizzle/0720_sealed_reseal_frozen.sql:211`: Guard baru mematahkan fixture test expiry voucher yang sudah ada.** Skenario: `apps/api/src/test/apology-voucher.test.ts:224` mengubah `issued_at` sebagai owner agar voucher tampak lama; trigger BEFORE UPDATE baru menolak perubahan kolom itu dengan `23514`, sehingga test “voucher yang lewat masa berlaku terbaca berstatus expired” berhenti sebelum memeriksa hasil API. **Perbaikan:** Buat fixture bertanggal lampau saat INSERT atau gunakan clock terkontrol; pertahankan guard append-only. **Usul test:** Jalankan `src/test/apology-voucher.test.ts` bersama `src/test/sealed-secret-reseal-frozen.test.ts` melalui `LEGEND_TEST_FILES` dan `heavy pnpm test`. Kegagalan ini disimpulkan dari kode, belum direproduksi dengan DB pada review ini.

## Pemeriksaan lain dan mitigasi

- `SECURITY DEFINER` mematok `search_path=pg_catalog, pg_temp`, menggunakan empat UPDATE statis dengan tabel `public` yang eksplisit, dan mencocokkan tenant, id, serta ciphertext lama. Tidak ditemukan jalur hijack nama objek atau perubahan kolom lain melalui fungsi. Trigger membandingkan seluruh record selain satu kolom sealed dan memeriksa pemilik fungsi; DELETE order/tender final tetap ditolak.
- Job membuka envelope baru dengan AAD yang sama dan membandingkan plaintext sebelum mengirimnya. Remaining tetap menghitung baris beku; aturan pensiun di runbook tetap menuntut failed dan remaining nol pada semua entri. Tidak ditemukan jalur pensiun prematur pada operasi normal. Pengecekan versi/panjang SQL sendiri tidak membuktikan autentikasi atau plaintext identik; envelope sampah yang tampak berversi baru juga tidak dapat dideteksi hanya dari remaining berbasis byte versi. Ini bagian risiko kompromi yang diterima, dengan cakupan tenant dikoreksi oleh P1.
- Tidak ditemukan writer/backfill produksi resmi voucher yang terblokir: service melakukan INSERT (`apology-voucher.service.ts:273`), sedangkan job memakai pass beku. DELETE voucher tetap dibatasi REVOKE yang sudah ada; trigger baru hanya BEFORE UPDATE. Tidak ada penghapusan voucher atau perubahan nilai uang yang ditemukan pada diff ini.
- Mitigasi murah utama untuk risiko envelope sampah adalah mempersempit siapa yang dapat SET ROLE, bukan menambah regex. Membership sementara hanya saat pemeliharaan mengurangi waktu paparan, tetapi tetap membuka akses API selama jendela itu apabila masih diberikan lewat `legend_app`.

Semantik lock dan konfigurasi SECURITY DEFINER diperiksa dengan Context7 terhadap dokumentasi resmi PostgreSQL: [row locks](https://www.postgresql.org/docs/17/explicit-locking.html), [lock timeout](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-LOCK-TIMEOUT), dan [fungsi SECURITY DEFINER](https://www.postgresql.org/docs/17/sql-createfunction.html). Baseline hak grup mengacu pada [SET ROLE](https://www.postgresql.org/docs/16/sql-set-role.html) dan [privilese PG17](https://www.postgresql.org/docs/17/ddl-priv.html).
