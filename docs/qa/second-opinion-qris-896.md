## Temuan

- **P1-1 — `apps/api/src/services/pos-order-payment.ts:287`**: Guard dana terbuka hanya dijalankan untuk `cash`, `qris`, dan `points`, sehingga tender `edc_card`/`edc_qris` standalone baru tetap diterima setelah uang QR diketahui terparkir. Skenario: QR Rp33.000 → manager force release → webhook paid terlambat memarkir Rp33.000 → kasir mendapat override supervisor standalone baru dan memasukkan slip EDC untuk seluruh sisa Rp33.000 → API membukukan tender `captured`, sementara dana QR Rp33.000 belum diselesaikan. `standalone` membuat `settlesEcrRequest` false (`:269`), tetapi melewati guard baru; `:548` memanggil `settlePosEdcStandalone` dan `:580` membukukan seluruh sisa. Route `apps/api/src/routes/pos-order.routes.ts:382` serta schema `packages/shared/src/pos/endpoints.ts:368` mengizinkan jalur ini tanpa request ECR terdahulu; `apps/api/src/services/pos-edc-standalone.ts:96` hanya memeriksa ledger EDC dan override. Ini melanggar keputusan CTO bahwa dana terbuka memblokir semua tender baru; pengecualian Q7 untuk pembukuan ECR yang sudah berjalan tidak membuktikan standalone ini dimulai sebelum dana QR diketahui. API standalone tidak mengirim penagihan terminal: celahnya adalah mengizinkan pencatatan pembayaran kedua melalui alur manual baru. Saran: Jalankan guard untuk standalone di cabang `!settlesEcrRequest`, termasuk sebelum persetujuan alur manual baru bila persetujuan itu mengarahkan kasir meminta pembayaran; pertahankan perlakuan Q7 untuk request ECR yang memang sudah berjalan. Usul test: Gabungkan fixture force release + late paid dengan terminal/PIN supervisor `pos-edc-standalone.test.ts`; uji kedua metode standalone, harapkan 409 `FUNDS_UNRESOLVED`, tanpa tender/ledger/approval-use baru, kemudian berhasil setelah dana diselesaikan.

- **P1-2 — `apps/api/src/services/payment.service.ts:1470`**: Penandaan final baru tidak memeriksa bahwa uang benar-benar tercatat; jawaban penyedia `paid` dengan nominal nol dapat menghentikan kedua jalur pemulihan dan meninggalkan pembayaran berikutnya tanpa evidence/jurnal. Skenario fault-injection: VA Duitku tersimpan sudah `expired` secara lokal, `provider_final_at` masih NULL → callback sah bernominal penuh memicu status read dengan reference benar, `statusCode:"00", amount:"0"` → adapter menerima nol (`apps/api/src/services/payment-duitku-wire.ts:109`, `:300`) → webhook masuk mismatch (`apps/api/src/services/payment-duitku-webhook.service.ts:388`) → `holdGatewayAmountMismatch` mengubah status menjadi `failed`; pencatatan dana keluar tanpa menulis apa pun karena `paid <= 0` (`payment.service.ts:1235`), tetapi tambahan `:1470` tetap mengisi `provider_final_at`. Webhook ditandai mismatch terminal (`payment-duitku-webhook.service.ts:458`) dan dikecualikan dari retry worker (`:645`); selector poll juga mengecualikan intent yang sudah final (`payment-live-code.ts:47`). Ketika status penyedia pulih menjadi paid nominal penuh dan webhook susulan hilang, tidak ada poll/retry lagi: nol evidence, nol dana terparkir, nol event penerimaan untuk jurnal. Skenario ini memerlukan jawaban penyedia tidak konsisten; tidak mengklaim kejadian tersebut sudah diamati di production. Saran: Perlakukan paid tanpa nominal positif sebagai jawaban belum meyakinkan dan tetap retry; jangan menyimpulkan rekonsiliasi final dari pemanggilan helper parkir yang tidak menghasilkan atau menemukan receipt positif tersimpan. Usul test: Callback sah pada VA expired + status paid nol → final tetap NULL, evidence/fund/event penerimaan nol, event masih dapat dicoba kembali; ubah status menjadi paid nominal penuh tanpa webhook baru → poll/retry berulang mencatat atau memarkir seluruh uang tepat sekali. Sertakan juga intent `failed` nonfinal, karena jalur poll `payment.service.ts:2777` kini dapat menandainya final setelah helper parkir mengembalikan no-op.
