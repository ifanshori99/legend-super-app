## Temuan

1. **P1 — Refund provider yang tidak mengirim webhook tidak terdeteksi sebelum refund baru.** `apps/api/src/services/payment.service.ts:3839`–`:3856` tidak memilih intent `paid` untuk poller; `apps/api/src/services/payment-refund.service.ts:643`–`:678` melepas reservasi ketika refund kita gagal tanpa memperoleh status transaksi provider. **Skenario:** pembayaran A Rp100.000 berstatus paid; refund kita R sedang diproses, provider secara terpisah sudah mengembalikan A, webhook hilang, lalu R gagal. Tidak ada fact atau hold, sehingga refund baru Rp100.000 dapat diajukan dan dikirim. Jika provider menerima payout baru, pembayar mendapat Rp200.000 dari pembayaran Rp100.000. Ini adalah `legend-w2td5`, saat ini P2; risiko uang keluar dua kali menjadikannya **P1 untuk gerbang rilis**, bergantung pada perilaku provider yang belum dibuktikan menolak payout kedua. Test `apps/api/src/test/refund-1035-a-pending-ref-own.test.ts:1470`–`:1486` mengonfirmasi batas poller dalam fixture, tetapi tidak memeriksa payout kedua. **Perbaikan:** sebelum melepas dana untuk refund berikutnya, periksa status provider secara andal atau tahan untuk rekonsiliasi; jawaban tidak tersedia tetap ditahan. **Usul test:** hilangkan webhook, set status A refunded, gagalkan R, ajukan dan setujui refund baru; pastikan tidak ada panggilan payout kedua, termasuk ketika pemeriksaan provider gagal atau tidak tersedia.

2. **P1 — Webhook sudah diterima tetapi retry tanpa hold membuka jeda refund ganda.** `apps/api/src/services/payment-provider-partial-refund.ts:320`–`:342` mengembalikan `retry` untuk refund sendiri yang sudah dicoba tetapi belum punya referensi; `:425`–`:429` juga dapat mengembalikan `retry` untuk status penuh. `apps/api/src/services/payment-webhook.service.ts:993`–`:995` menyisakan event untuk retry, sedangkan guard `apps/api/src/services/payment-provider-refunded-guard.ts:114`–`:132` tidak memakai event tersebut sebagai blokir. **Skenario:** intent paid Rp100.000, R Rp100.000 sudah dicoba dan masih approved tanpa provider ref; provider secara terpisah mengembalikan pembayaran dan webhook signed tiba. Pada jalur status transaksi utama, stamp dapat tidak ditulis karena R sudah dihitung sebagai uang terkirim (`apps/api/src/services/payment.service.ts:3467`–`:3471`, `:3540`–`:3549`); recorder meminta retry tanpa fact atau hold. R lalu gagal sebelum worker mengulang event, dan refund baru dapat diajukan serta dikirim di jeda itu. Pintu refund ID provider juga dapat berhenti di `retry` sebelum membuat fact. Uang keluar dua kali bila provider menerima payout baru. **Perbaikan:** simpan hold yang memblokir refund dan penggunaan dana dalam transaksi yang menerima laporan valid, termasuk ketika identitas echo belum pasti, lalu selesaikan setelah R final; jangan mengandalkan retry event saja. **Usul test:** gunakan barrier setelah webhook pertama menghasilkan retry, gagalkan R, ajukan refund baru sebelum worker berjalan dan pastikan tertahan tanpa payout; ulangi untuk webhook status penuh dan refund ID, replay, serta race worker dengan kegagalan R.

3. **P1 — Migrasi 0656 menebak ID provider lama sebagai status refund penuh.** `apps/api/drizzle/0656_provider_refund_id_kind.sql:35`–`:40` mengubah hold lama menjadi `synthetic_full` jika ID refund sama dengan `payment:` ditambah payment ref; `:61`–`:68` juga menebak dari prefix ketika payment ref null. ID refund provider yang asli boleh berbentuk itu, dan mismatch webhook lama menyimpan ID provider asli serta payment ref (`apps/api/src/services/payment-webhook.service.ts:1739`–`:1765` pada `6075e2bb6`); migrasi `0650_refund_recon_hold_payment_ref.sql:1`–`:6` juga membiarkan hold sebelumnya tanpa payment ref. **Skenario:** hold mismatch lama mencatat refund provider asli `payment:foo` Rp30.000 atas transaksi `foo` Rp100.000. Migrasi mengubahnya menjadi status penuh `foo`; `apps/api/src/services/refund-recon-hold.service.ts:367`–`:406` kemudian menghitung sisa seluruh transaksi, bukan Rp30.000, dan `:516`–`:525` menolak pilihan `not_this_intent`. Jika `foo` tidak dapat diikat, hold dapat macet; replay dengan ID event baru juga dapat membuat hold kedua dalam namespace `provider`. Dua ID lama berbeda yang sama-sama dipetakan ke `(synthetic_full, foo)` dapat pula menggagalkan indeks unik `0656_provider_refund_id_kind.sql:82`. **Perbaikan:** klasifikasikan hanya bila asal fact dapat dibuktikan dari event atau provenance; pertahankan kasus ambigu dalam keadaan tertahan untuk verifikasi, tanpa menebak nilai atau menggabungkan identitas. **Usul test:** migrasikan hold mismatch lama dengan ID `payment:foo`, nominal 30, payment ref `foo` dan evidence 100; uji count, `not_this_intent`, replay dan isolasi tenant. Tambahkan hold lama tanpa payment ref serta dua ID yang berpotensi menjadi kunci sintetis sama; migrasi tidak boleh salah menghitung, menggandakan hold, atau gagal karena benturan.

4. **P1 — Migrasi 0656 memutus penulis refund lama selama deploy.** `apps/api/drizzle/0656_provider_refund_id_kind.sql:10` dan `:83` mengganti unique key fact refund menjadi empat kolom, tetapi recorder pada `6075e2bb6`, `apps/api/src/services/payment-provider-partial-refund.ts:461`–`:467`, masih memakai `ON CONFLICT` dengan tiga kolom. Penulis hold lama juga tidak mengisi kolom jenis, sedangkan check baru pada migrasi `:85` mewajibkannya untuk ID yang tidak null. `deploy/single-vm/deploy.sh:40`–`:43` menjalankan migrasi sebelum mengganti API dan worker; `apps/api/src/db/migration-session.ts:3`–`:8` menegaskan proses lama tetap melayani. **Skenario:** sesudah migrasi commit dan sebelum proses lama diganti, webhook refund provider masuk; insert fact gagal karena target konflik tidak lagi punya unique key yang cocok, atau insert hold bernama gagal check. Transaksi pencatatan dan blokir terkait tidak terpasang; jendela berlangsung lebih lama bila audit atau restart gagal, dan refund lain dapat diproses sebelum retry memulihkan fakta. **Perbaikan:** gunakan tahapan migrasi yang kompatibel dengan kedua versi, atau hentikan penulis dan lalu lintas selama migrasi dengan pemulihan event serta blokir yang terbukti aman; sertakan rencana rollback. **Usul test:** jalankan penulis `6075e2bb6` terhadap skema setelah 0656, kirim refund dan mismatch hold pada jeda migrasi, lalu ganti ke versi baru dan retry; pastikan tidak ada payout kedua, event tidak hilang dan tepat satu fact atau hold aman tersedia, termasuk saat penggantian proses gagal.
