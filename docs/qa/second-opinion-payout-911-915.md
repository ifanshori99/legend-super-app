1. **P2 — Proposal yang ditarik lalu diajukan ulang menjadi duplikasi palsu pada rekonsiliasi.** `apps/api/src/services/payroll-payout-recon.service.ts:964` mensyaratkan tidak ada attestation yang menunjuk bukti historis agar binding-nya dapat dikecualikan; pemeriksaan pada `apps/api/src/services/payroll-payout-recon.service.ts:974` kemudian menghasilkan `binding_duplicate`. **Skenario:** finance mengusulkan koreksi K1, menariknya lewat fungsi 915, mengusulkan K2 dengan byte berbeda untuk item yang sama, lalu orang kedua menyetujui K2 secara sah. Withdraw mempertahankan attestation propose K1 dan menambah attestation withdraw (`apps/api/drizzle/0658_payout_proposal_withdraw.sql:845`); binding K1 juga permanen. Karena itu syarat pengecualian K1 selalu gagal, meskipun tidak ada pembayaran melalui K1. Padanan overpaid memakai attestation withdraw pada `apps/api/drizzle/0658_payout_proposal_withdraw.sql:947`. Recon menulis exception dan menahan slip, termasuk retry setelah retur yang sah. **Perbaikan:** bedakan binding operasi yang terbukti berakhir `withdrawn` tanpa completion dari binding dua operasi selesai; pertahankan histori dan larangan memakai ulang bukti. **Usul test:** perluas `[915-withdraw-correction-repropose-new-proof]` pada `apps/api/src/test/payroll-payout-915-withdraw.test.ts:1014` dan padanan overpaid pada `apps/api/src/test/payroll-payout-915-withdraw.test.ts:1043` dengan recon setelah K2 selesai. Harapkan nol flag/exception, binding serta log K1 tetap tersimpan, jurnal tepat satu, dan kontrol dua completion tetap ditolak. Temuan ini mengenai alur withdraw baru; bukan pengulangan skenario mengganti bukti proposal terbuka pada laporan 905. Tindak lanjut: `legend-87dur`.

2. **P2 — Migrator non-superuser tidak mendapat hak mengelola role grantor yang sudah ada.** `apps/api/src/db/provision-roles.ts:1243` memberi membership `legend_payout_grantor` kepada login grantor, tetapi bootstrap pada `apps/api/src/db/migrator-role.ts:207` hanya memberi ADMIN pada `legend_app`, `legend_payout`, dan login app/worker. Grup dan login grantor deploy ini tidak ikut. **Skenario:** grup `legend_payout_grantor` sudah dibuat bootstrap atau migrator database lain pada cluster yang sama; database baru dimiliki migrator NOSUPERUSER CREATEROLE yang disiapkan lewat `provisionMigrator`. Migrasi 0653 melewati CREATE ROLE karena grup sudah ada (`apps/api/drizzle/0653_payout_step_grants.sql:31`). Setelah migrasi, provisioning login baru harus memberi membership grup tadi; pada PostgreSQL 16+ CREATEROLE tanpa ADMIN atas grup itu tidak cukup, sehingga jalur tersebut gagal dengan 42501. Bila login grantor sendiri sudah dibuat administrator lain, pembaruan login juga membutuhkan ADMIN yang belum disiapkan. Fixture justru memberi hak grup ini secara manual pada `tests/db-role-provisioning.test.mjs:1324`, sehingga test tersebut tidak membuktikan jalur bootstrap production. Instalasi yang membuat grup dan login melalui migrator yang sama tidak terkena kondisi ini. **Perbaikan:** teruskan identitas login grantor deploy ke bootstrap migrator dan beri ADMIN pada grup serta login yang sudah ada, dengan INHERIT FALSE dan SET FALSE seperti role lain. **Usul test:** buat grup/login grantor sebagai bootstrap, siapkan database milik migrator baru, lalu jalankan `provisionMigrator` nyata, migrasi, dan `provisionRoles({grantorUrl})` sebagai non-superuser. Semuanya harus berhasil tanpa GRANT manual fixture; pertahankan kontrol penolakan role berbahaya. Ini kegagalan penyelesaian deploy/provisioning, bukan klaim bahwa seluruh SQL 0652–0659 gagal pada instalasi baru. Tindak lanjut: `legend-fwx7l`.

3. **P2 — Variabel worker dapat melewati kewajiban grantor pada startup API langsung.** `apps/api/src/config/env.ts:825` menerima keberadaan `WORKER_DATABASE_URL` sebagai pengecualian grantor wajib, sedangkan field itu hanya string opsional pada `apps/api/src/config/env.ts:101`. **Skenario:** API production di custom deploy mewarisi `WORKER_DATABASE_URL` dari environment bersama, tetapi grantor belum diisi. Validasi grantor lolos, dan entrypoint API tetap membuat aplikasi serta membuka listener (`apps/api/src/server.ts:46`, `apps/api/src/server.ts:79`); tidak ada pemeriksaan bahwa proses itu benar-benar worker. Pool grantor production menjadi null (`apps/api/src/db/grantor.ts:69`) dan langkah payout kemudian menjawab 503 (`apps/api/src/services/payroll-payout-grant.service.ts:110`). Bahkan string worker yang bukan URL cukup untuk melewati predikat ini. Compose resmi menolak variabel worker pada service API (`deploy/single-vm/check-compose-env.mjs:63`), sehingga temuan terbatas pada start langsung/custom deploy. **Perbaikan:** periksa kewajiban grantor pada entrypoint API berdasarkan proses yang dijalankan; pertahankan pengecualian pada entrypoint worker dan edge yang sebenarnya. **Usul test:** jalankan entrypoint API production dengan grantor kosong dan worker URL terisi; harus keluar sebelum listen. Kontrol API dengan grantor harus hidup, dan entrypoint worker sebenarnya tetap boleh tanpa grantor. Ini pelanggaran syarat boot `legend-786te` dan gangguan ketersediaan payout, bukan bypass pembayaran; penolakan uang dengan 503 tetap berlaku. Tindak lanjut: `legend-9n1mu`.
