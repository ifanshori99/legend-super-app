## Temuan

1. **P1 — Hold mismatch lama yang kecil menelan kenaikan konservatif R2, sehingga kredit DP tetap terbuka.** `apps/api/src/services/payment-webhook.service.ts:1789`–`:1794` menghitung nominal penuh yang benar, tetapi `holdRefundReferenceMismatch` pada `:886`–`:906` hanya melakukan INSERT dengan `onConflictDoNothing()` dan langsung kembali ketika bentrok. Unique key mengikat tenant, intent, jenis/id refund, dan transaksi (`apps/api/src/db/schema/refund-recon-holds.ts:78`–`:86`), tanpa nominal. **Skenario:** T1 mempunyai R1 Rp30.000; T2 adalah DP Rp100.000. Event signed keyed R1, refund Y/payment T2, nominal terbaca Rp30.000 membuat hold `REFERENCE_MISMATCH` Rp30.000 pada T2. Event baru dengan key, Y, dan T2 yang sama tetapi `amount: "80000.0"` menghitung penahanan Rp100.000. INSERT bentrok dengan hold terbuka lama; penahanan tetap Rp30.000, tanpa fact atau penanda full refund. Query kredit hanya memotong nominal hold tersebut (`apps/api/src/services/reservation-deposit-credit.ts:178`–`:190`, `:234`–`:240`), sehingga Rp70.000 masih tersedia pada pool DP. Bila Rp80.000 sudah dikembalikan penyedia, refund ditambah kredit terpakai menjadi Rp150.000 dari pembayaran Rp100.000. Refund baru dan settle manual memang tertahan karena hold masih terbuka; celahnya melalui kredit DP. Kunci intent/DP menyerialkan kedua laporan tetapi tidak menaikkan nominalnya. **Invarian:** I3/I10(b). Ini memakai hold yang masih terbuka, bukan keberatan atas keputusan finance atau replay sesudah resolve. **Perbaikan:** naikkan hold terbuka dengan `greatest` di bawah kunci intent/DP yang sudah dipegang, atau simpan penahanan konservatif terpisah dengan dedup stabil. **Usul test:** awali dengan hold Y/T2 Rp30.000, lalu kirim event invalid/hilang nominal dengan identitas sama; assert penahanan efektif Rp100.000, kredit asli/pindahan nol, apply Rp70.000 ditolak, serta replay tanpa jurnal atau hold tambahan. Gunakan dua koneksi dengan barrier untuk kedua urutan perolehan kunci; urutan readable dahulu saat ini mempertahankan Rp30.000. Test baru selalu mulai tanpa hold (`refund-1077-r2-mismatch-unreadable-amount.test.ts:60`–`:61`); pembuktian DP dan kedua urutan kunci masih `it.todo` (`:180`–`:181`).

2. **P1 — Namespace `invalid-h:` masih dapat bertabrakan dengan ID penyedia biasa dan menyerap bukti refund lain sesudah resolve.** `apps/api/src/services/payment-webhook.service.ts:836`–`:839` memisahkan hasil hash dari bentuk `invalid:`, tetapi kedua bentuk invalid tetap diteruskan sebagai kind `provider` (`apps/api/src/services/payment-provider-partial-refund.ts:1346`–`:1349`). Parser menerima string ID apa pun sepanjang 1–100 karakter (`apps/api/src/services/payment-doit-refund-webhook.ts:74`–`:86`), termasuk hasil hash itu sendiri. **Skenario konkret, tanpa mencari benturan SHA-256:** L = `"L".repeat(93)`; `invalidReportHoldRefundId(L)` adalah `invalid-h:1546a4c7fa72d07396a82cda00ccee3ab7a3e6ae4fa6b8948df7adedf245dc33` (74 karakter), sebut H. Pada T Rp100.000 sudah ada R completed Rp20.000/ref X dan R2 approved Rp80.000 tanpa trace penyedia. Event signed keyed R dengan refund ID L dan nominal invalid memasang placeholder Rp100.000 ber-ID H. Finance membuktikan laporan L bukan refund intent ini dan menutupnya `not_this_intent`. Berikutnya datang refund nyata yang berbeda: event signed keyed R, **ID penyedia literal H**, payment T, nominal Rp60.000. Ini ID yang diterima parser; ref berbeda dari X membuat updater menolak melalui callback konflik (`payment-webhook.service.ts:1903`–`:1927`, `payment-refund.service.ts:4129`–`:4137`). Helper mencari kunci provider/H/T yang sama (`payment-provider-partial-refund.ts:1439`–`:1441`), menemukan placeholder resolved Rp100.000, lalu menganggap Rp60.000 sebagai bukti lama karena tidak melebihi `maxHeld` (`:1484`–`:1488`). Tidak ada fact atau hold baru. Settle R2 kembali memenuhi guard/cap (`payment-provider-refunded-guard.ts:124`–`:132`, `payment-refund.service.ts:3809`–`:3826`), sehingga Rp20.000 + Rp60.000 + Rp80.000 dapat keluar dari pembayaran Rp100.000. Ini alias antara identitas buatan dan identitas literal yang sah menurut parser, bukan collision kriptografis. Varian bentuk pendek `invalid:<id>` mempunyai masalah domain yang sama. **Invarian:** I1/I2/I7/I8; keputusan atas laporan L tidak membuktikan laporan H adalah replay. **Perbaikan:** pisahkan domain dedup bukti invalid dari ID penyedia, dengan kompatibilitas hold lama; mengganti prefix string saja tidak cukup selama parser menerima prefix tersebut sebagai ID normal. **Usul test:** gunakan L dan H persis di atas melalui matched webhook, resolve placeholder, lalu kirim H/T Rp60.000; assert bukti baru tetap ditahan, settle R2 dan kredit DP ditolak, tanpa fact/jurnal rekaan. Uji kedua pintu matched/recorder dan resolve-versus-laporan dengan dua koneksi; kontrol ID L berulang tetap satu hold dan panjang 92/93/100 tetap aman.

3. **P2 — Replay laporan invalid tanpa refund ID dapat membuka hold kedua setelah referensi R terisi.** Identitas pada `apps/api/src/services/payment-webhook.service.ts:1826`–`:1827` memakai `facts.refundId ?? refund.providerRef ?? refund:<R>`, sehingga bergantung pada keadaan R saat diproses. **Skenario:** R approved yang sudah dicoba kirim tetapi belum mempunyai `providerRef` menerima event signed keyed R, payment T, tanpa refund ID dan tanpa nominal terbaca. Parser tetap mencocokkannya lewat key (`payment-doit-refund-webhook.ts:187`–`:199`, `:267`–`:268`); hold pertama bernama `invalid:refund:<R>`. Event sukses sah berikutnya dengan ID X dan nominal tepat R melengkapi R dan mengisi `providerRef = X` (`payment-refund.service.ts:4164`–`:4169`, `:883`–`:888`). Redelivery laporan invalid semula dengan envelope ID baru sekarang menghasilkan `invalid:X`, sehingga INSERT membuat hold kedua. Bahkan retry **stored event yang sama** bisa melakukannya bila proses pertama berhenti sesudah transaksi hold commit (`payment-webhook.service.ts:1816`–`:1834`) sebelum event ditandai ignored (`:1865`); worker mengulang received/failed (`:2681`–`:2709`, `:2785`), sedangkan event ID hold dihitung dari kunci yang berubah, bukan dari ID stored event (`payment-provider-partial-refund.ts:1384`–`:1400`). Bila hold pertama sudah diselesaikan finance, replay bukti identik kembali menahan dana. Ini konservatif, bukan pembayaran berlebih, tetapi satu laporan menghasilkan dua kasus rekonsiliasi dan dapat memblokir sisa refund/DP lagi. **Invarian:** stabilitas identitas replay dan aturan bukti sama I7 belum berlaku pada fallback tanpa ID. **Perbaikan:** gunakan identitas fallback dari fakta event/key R yang tetap, tanpa menggantinya dengan referensi R yang muncul kemudian; pertahankan dedup hold yang sudah tersimpan. **Usul test:** event invalid keyed tanpa ID saat ref NULL, lalu sukses X, lalu replay payload invalid; assert hanya satu hold sepanjang transisi. Tambahkan barrier sesudah commit hold dan sebelum penandaan event untuk varian worker retry, serta varian hold pertama telah di-resolve.
