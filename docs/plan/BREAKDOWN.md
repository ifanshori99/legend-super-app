## Conventions

- One epic per workstream (`WS-00`..`WS-14`, label `ws-xx`, label `epic`); every task is a child of its epic. Existing `legend-6gh` (Design System), `legend-bi3` (119connect inventory) and `legend-vue` (this breakdown) were re-parented under the WS-00 epic.
- Titles: `WS-xx CT|FE|BE|INT|EXT: …`. `CT` = contract (packages/shared Zod/types/events/adapters/fixtures). `INT` covers integration, QA and infra (label tells which). `EXT` = human/vendor dependency.
- Labels: `ws-xx`, one layer label (`contract`, `fe`, `be`, `integration`, `qa`, `infra`, `human`) and one agent hint (`opus`, `codex`, `sonnet`, `zcode`). Deferred items also carry `pascarilis`.
- Priority: P0 = WS-00 + all contracts + EXT blockers; P1 = FE; P2 = BE; P3 = integration/QA/deploy; P4 = deferred Pascarilis [P1] features (status `deferred`).
- Each description has PRD refs (section + feature), scope, **suggested** owned paths (coordinator finalizes ownership per thread brief), `reuse candidate: 119connect <module>` where the §7 table / inventory applies, and the agent hint. `--acceptance` holds criteria IDs + the layer gate (CT: schemas+fixtures test; FE: DESIGN.md tokens, white bg + dark, 360px/desktop, states, mock mode; BE: migration + enforced RLS + isolation tests; INT: real API + e2e).
- Dependencies are `blocks` edges only where real (contract → FE/BE, schema → services, cross-module events). All FE tasks depend on `legend-6gh` and `f00shell`. Integration beads depend on every FE/BE bead of their WS **except** real-vendor adapters (integration runs on fakes; vendor adapters feed WS-13 staging e2e).
- `bd dep cycles`: **no cycles**.

## Phases

1. **Contracts (P0)** — WS-00 core → WS-00 rbac/events/adapters/audit/metrics/text/api-client → per-WS contracts. Unblocks FE and BE.
2. **Frontend (P1)** — `f00shell` (route areas + layouts on legend-6gh) then one FE bead per screen/flow group per WS, built on fixtures via API-client mock mode.
3. **Backend (P2)** — WS-00 foundations (RLS, outbox, audit, storage) run early as P0 in a parallel lane; WS-01 org schema/RLS is the gate for all tenant tables (inventory copy order 1→5). Module BE follows the dependency chain.
4. **Integration / QA / deploy (P3)** — one `INT` per WS swaps mocks for the real API; WS-13 runs isolation, staging e2e (flows A–Z), load, security, chaos, a11y, whitelabel, restore; WS-00 infra builds images, Caddy, staging, backups, monitoring, edge image, prod import, go-live runbook.

## Wave plan (max 6 concurrent agent threads)

Assumes legend-6gh lands before W02 ends and EXT items resolve before their dependents. Waves are file-disjoint by default (different WS/domain dirs); where two beads of the same WS share a wave the coordinator should give each a distinct path set or use `--worktree`. `bd ready` is the live source of truth — this is a plan, not a lock.

## PRD ambiguities and contradictions

### Need a decision (asked in the handover)

1. **Clickable mockup vs FE-first.** §3 F1 wants an owner-approved clickable mockup by 2 Nov; this plan builds real FE screens on mock data instead. Proposal: FE beads with fixtures _are_ the clickable mockup, reviewed per WS. No separate mockup beads were created.
2. **API framework.** §7 lists Hono or Fastify; the repo (Starter v0.1.0, "template default" allowed by §7) is Express 5 + Better Auth. Plan assumes Express 5 stays.
3. **Money types.** §6 says money is BIGINT rupiah, but `recipes.theoretical_cost_idr` and `stock_ledger.unit_cost_idr` are NUMERIC(14,4) and `ai_jobs.cost_idr` is NUMERIC(12,2). Proposal: BIGINT for every amount that is posted or paid; NUMERIC(14,4) only for per-unit cost and quantity; settled in `c00core`.
4. **Offline edge front end.** §5 serves `/pos`, `/kds`, `/wifi` and so on from the edge, but the edge component list has no web or static server, and how the POS PWA works offline is not specified. Proposal: run the web container in edge mode with local DNS, decided in `b02runtime`.
5. **Wi-Fi login during an internet outage.** WhatsApp reverse OTP needs the cloud webhook, so new guests cannot log in to Wi-Fi while offline. Choose one: grace access, staff-issued vouchers, or accept it.
6. **Wi-Fi +1 hour per Rp30.000.** Is it per multiple of Rp30.000 or once per order? (§3 F25, flow X.)
7. **Unnamed providers.** These block the deploy and adapter beads: VPS or host, CDN, S3 host, email provider, LLM provider, maps or geofence, and which EDC banks. Also the status of the overdue accounts (DOIT, Meta, ojol applications due 28 Oct) and the lock and Wi-Fi vendors (due 2 Nov).
8. **Schedule capacity.** Roughly 46 waves at 6 concurrent threads is tight for feature-complete on 30 Nov. Hardware installs on 5 Dec, one day before the 6 Dec code freeze, so real ECR, lock and Wi-Fi field tests land after freeze. Should concurrency go to 8–10 for FE and zcode waves, or should some modules plan for the go/no-go feature-flag fallback?
9. **100+ standard reports.** §3 F36 gives no list. Plan: the agent proposes a catalog in `c11metrics` for owner approval.
10. **Tenant scoping of global tables.** `login_challenges` and `wa_inbound_messages` are global yet carry `tenant_id`. With a WhatsApp number per tenant, the webhook must resolve the tenant from the receiving number. Proposal: no RLS on these two tables, with service-layer scoping and a test.

### Resolved by assumption (flag if wrong)

- **Workstream numbering.** D34 and §7 say WS-01..WS-13, but the WS map also has WS-14 (Operasional Harian). Plan uses WS-00..WS-14.
- **Domain event names.** The PRD names none. Plan uses `<aggregate>.<past_verb>`, catalogued in `c00events`.
- **ID types.** ULID primary keys (orders, order_items, access_tickets) are referenced by UUID-typed foreign keys in §6. Plan uses one id type per aggregate across all foreign keys, fixed in `c00core`.
- **`reservations.table_ids UUID[]`** has no foreign-key integrity. Plan uses a join table plus a tstzrange exclusion constraint (`b08resv`).
- **`vendor_id`** in the maintenance tables has no `vendors` table. Plan maps it to `suppliers`, or adds a vendor type (`b14equip`).
- **Immutability.** `journal_lines`, `audit_logs`, `access_events`, `gateway_webhook_events` and `distribution_lines` are not marked append-only. Plan treats them as append-only.
- **Edge replication.** It is inconsistent between `entitlement_*`, `subscription_*` and `lock_credentials`. Plan replicates whatever an offline ticket or POS sale needs (FAC-03), decided in `c09fac`.
- **KDS ≤ 2 s (KDS-01).** Plan measures it from fire (after payment confirmation in pay-first mode), not from customer submit.
- **Load test.** §7 says "300 seat"; plan uses the §2 numbers: 300 devices, 150 sessions, 600 items/h, 40 staff devices.
- **Shower tax treatment** is pending a tax consultant (A20). The tax engine supports a separate facility rule; its value is configuration.
