# Contract conventions (WS-00 core)

Bead `legend-6gu` · PRD v1.7 §3 "Kontrak Bersama", §6 conventions, TEN-02/TEN-03, ORD-06.
Code: `packages/shared/src/core` (import `@starter/shared/core`). Tests: `tests/core-contract.test.mjs` (runtime) and `packages/shared/src/core/type-tests.ts` (compile time).

Every domain contract (`CT` bead) builds on these rules. Change them only through a WS-00 bead.

## Decisions

### D-CORE-1 Ids: UUID everywhere, ULID for time-ordered aggregates, one `uuid` column type

PRD §6 says all ids are UUID, but operational events use ULID, and several ULID primary keys (orders, order_items, kitchen tickets, stock_ledger, access tickets) are referenced by UUID-typed foreign keys (for example `order_items.order_id`, `stock_ledger.source_id`).

- **Postgres:** every id column, primary or foreign, is `uuid`. A ULID is 128 bits, so it is stored losslessly in a `uuid` column (`ulidToUuid` / `uuidToUlid`). Byte order equals time order, so index locality and ordering are kept. This keeps every §6 foreign-key type as written.
- **Wire and TypeScript:** one id type per aggregate everywhere it appears. UUID aggregates use `uuidIdSchema<"XId">()`; ULID aggregates use `ulidIdSchema<"XId">()` and always travel as the 26-character ULID text, including in foreign-key fields of other aggregates (for example `payment.orderId`). The API converts at the DB boundary (a Drizzle custom type in the BE schema bead).
- **Generation:** UUIDs come from Postgres `gen_random_uuid()` or `crypto.randomUUID()`. ULIDs come from `createUlidFactory()` (monotonic within a millisecond, so one device's outbox stays ordered offline) or `createUlid()`.
- Ids are branded per aggregate (`TenantId`, `OutletId`, …), so mixing them is a type error.

### D-CORE-2 Money: BIGINT whole rupiah for amounts, NUMERIC(14,4) only per-unit cost and quantity

PRD §6 says money is BIGINT rupiah, but `stock_ledger.unit_cost_idr` and `recipes.theoretical_cost_idr` are NUMERIC(14,4) and `ai_jobs.cost_idr` is NUMERIC(12,2). Tech-lead decision:

- **Any amount that is posted, paid, billed, allocated or reported** (order totals, payments, journals, payroll, profit share, budgets, stock value totals): `BIGINT` whole rupiah. TypeScript/JSON: `Idr`, a branded safe integer (JSON `number`; every realistic amount is far below 2^53). Field suffix `Idr` (`totalIdr` ↔ `total_idr`).
- **Per-unit cost and quantity** (`stock_ledger.quantity`, `stock_ledger.unit_cost_idr`, `recipes.theoretical_cost_idr`, yields, UOM factors): `NUMERIC(14,4)`. TypeScript/JSON: `Decimal4`, a decimal string such as `"0.0180"` (the form `pg` returns), computed as scaled bigint, never as a float.
- **`ai_jobs.cost_idr`** (per-call estimate, fractions of a rupiah): `NUMERIC(14,4)` instead of NUMERIC(12,2), so there is one decimal type. Totals derived from it for reports or quotas are rounded to `Idr`.
- Converting between the two is always explicit and rounded: `extendCostIdr(quantity, unitCost, mode)`, `unitCostOf(totalIdr, quantity, mode)`.
- **Rounding is explicit.** Every helper that can produce a fraction takes a `RoundingMode` (`half_up` = half away from zero, `half_even`, `down`, `floor`, `ceil`). Which mode and cash increment a tenant uses is configuration (PRD F11 "aturan pembulatan", WS-05 tax contract), not code. `roundToIncrement` returns the rounded amount and the rounding line (`orders.rounding_idr`).
- **Splits sum exactly (ORD-06).** `allocateIdr(total, weights)` / `splitIdrEvenly` use the largest-remainder method with deterministic index tie-breaks; use them for split bills, combo revenue allocation, service-charge pools and profit share (weights in basis points, 10,000 = 100%).

### D-CORE-3 Tenant from domain or token, never from the client (TEN-02)

- **Provenance is enforced at runtime, not only by types.** `TenantContext` and `OutletScope` are valid only if the server minted them: an internal WeakSet registry (`core/trust.ts`, exported from no entry point) records every minted object. Plain objects, JSON round-trips, `structuredClone` and spread copies are never members.
- **Minting is server-only.** `@starter/shared/core/server` exports `establishTenantContext({ tenantId, brandId, source })` (`source` in `domain | session | device | mcp_token | job | webhook`), `establishOutletScope(tenant, assignment)` and `establishScopedTenantContext(tenant, assignment)`. It throws at import time where a DOM exists, and the browser-safe `@starter/shared/core` exports only the checks. Import the server entry only from `apps/api` and the edge runtime, with values the server resolved itself (host name → `tenant_domains`, verified token, job row, receiving webhook account; outlet reach from verified role assignments, which the RBAC contract `legend-0mc` expands from brand or station level to outlet ids).
- **Service boundaries assert.** Services take `ScopedTenantContext` (or `TenantContext`) and call `assertTrustedScopedContext` / `assertTrustedTenantContext` first, never accept a bare `tenantId` from the request. An `OutletScope` is bound to its tenant; pairing it with another tenant's context fails.
- Request schemas are built with `clientInputSchema({...})`: declaring `tenantId` / `tenant_id` is a compile error and throws at module load; parsing is strict, so a submitted `tenantId` is rejected.
- The database enforces the same with RLS and `SET LOCAL` (bead `legend-73d`). `login_challenges` and `wa_inbound_messages` resolve the tenant from the receiving WhatsApp number (`source: "webhook"`) and are service-scoped without RLS (coordinator decision).
- **TEN-03.** `isOutletInScope(scope, outletId)` and `assertOutletInScope` are the single check; an untrusted scope throws `TypeError` (fail closed). Lists, reports, exports, Tanya AI and MCP derive their outlet filter with `outletIdsForQuery(scope, requested?)`: nothing requested → the whole scope (`{ kind: "all" }` or the assigned outlets); any requested outlet outside the scope → `CoreError` `OUTLET_OUT_OF_SCOPE` (403).
- **TEN-03 outlet isolation layers (decision, bead `legend-tjey`).** _PRD reading:_ the PRD makes RLS mandatory for the **tenant** boundary — §2 "Isolasi multi-tenant" ("Setiap tabel milik tenant memiliki `tenant_id` dan dilindungi PostgreSQL RLS sekaligus pemeriksaan di service layer"), §3 "Isolasi Data", §6 "Konvensi multi-tenant" ("(T) … `tenant_id` … dilindungi Row Level Security"), Stack "Isolasi tenant: PostgreSQL RLS dengan `SET LOCAL`". For **outlets** it requires the outcome, not the mechanism: §2 "Cakupan outlet ditegakkan untuk role yang dibatasi per outlet", §6 "Tabel operasional juga membawa `outlet_id` untuk cakupan per outlet", TEN-03 (reports, exports, Tanya AI, MCP), and "Catatan Implementasi Arsitektur → Isolasi berlapis": "Service layer memeriksa ulang izin dan cakupan outlet"; Tanya AI never writes SQL and every tool checks the outlet scope on the server (§3 Kelompok E "Arsitektur Berbasis Tools"). So app-layer outlet enforcement is PRD-conformant, and DB-level outlet RLS is **not strictly required**. _Decision:_ enforce it at the database anyway as the second layer the PRD asks for in "Isolasi berlapis" and R16 ("RLS, cakupan outlet"; isolation tested in CI), because a single forgotten service filter would otherwise leak another outlet's rows. Layers:
  1. **Service layer (primary, gives the error).** `assertOutletInScope` / `outletIdsForQuery` as above; an explicitly requested outlet outside the scope → `OUTLET_OUT_OF_SCOPE` (403).
  2. **Database (backstop).** Migration `0032_outlet_rls` adds `app.enforce_outlet_rls(regclass)` next to `app.enforce_tenant_rls`: a RESTRICTIVE `outlet_isolation` policy (USING + WITH CHECK) reading `app.outlet_ids`, which `withTenant` installs from the server-minted scope. Semantics, all fail closed: unset/empty → error `42501` "outlet scope context is required"; `'*'` (only for a `{ kind: "tenant" }` scope — tenant- and brand-wide roles, guest/QR/public reads, jobs) → every outlet **of the current tenant** (the tenant policy still applies); a JSON array of uuids → exactly those outlets (`[]` → nothing); anything else → error "outlet scope context is malformed". Code that sets `app.tenant_id` by hand (seed, test fixtures) must also set `app.outlet_ids`.
  3. **Which tables.** Every tenant table whose `outlet_id` is `UUID NOT NULL` gets the policy in the same migration that creates it (call `app.enforce_outlet_rls` after `app.enforce_tenant_rls`); the catalog guard `src/db/outlet-rls.test.ts` fails CI otherwise. Allowlisted: `payment_link_tokens` (read before any tenant/outlet context, see the TEN-02 allowlist). Tables with a **nullable** `outlet_id` (tax rules/settings, service-charge rules, journals, audit log, domain events, notifications, tenant integrations, payment routing rules) hold tenant/brand-level rows that outlet roles legitimately read, so they keep the service-layer filter only.
  4. **Observable effect.** A by-id read or write of another outlet's record now behaves like a missing row (404 `NOT_FOUND`), the same answer as cross-tenant, so the response does not reveal that the record exists. Station-level narrowing stays in the service (next bullet): RLS stops at the outlet.
- **Station scope on station-bound resources (legend-fsb7).** A station assignment expands to its outlet only where the database needs an outlet to filter: a station-bound route authorizes a `{ type: "station" }` target (`requireStationPermission`) and mints an outlet context for that station's outlet. The service must then re-assert the station from the same snapshot (`assertStationPermission`) or filter the rows with `permittedStationIds` (`stationReachOf`) and fail closed when the station of a resource cannot be determined. `outletReachOf` keeps giving a station-only grant no outlet-wide query reach, so non-station routes stay closed. A station-aware list or ticket gate (`requireStationScopePermission`) mints the union of the outlet/brand reach and the outlets of the stations a station grant reaches, so outlet A plus station B reaches both outlets while the service still narrows outlet B to station B (legend-cy2e).
- Ids normalize on parse (UUID lowercase, ULID uppercase), so comparisons are plain `===`.
- Two copies of the shared package in one process would not trust each other's objects (fails closed). Keep `@starter/shared` a single workspace dependency.

### D-CORE-4 Errors

Envelope: `{ "error": { "code", "message", "details"?: [{ field, message }], "requestId"? } }`, the starter's shape. `code` is stable `UPPER_SNAKE_CASE`; the UI maps it to catalog text. `message` is a safe Indonesian fallback. Core codes and their HTTP status live in `coreErrorHttpStatus` (starter codes plus `TENANT_CONTEXT_REQUIRED`, `OUTLET_OUT_OF_SCOPE`, `FEATURE_DISABLED`, `CONFLICT`, `IDEMPOTENCY_KEY_REUSED`, `PRECONDITION_FAILED`, `RATE_LIMITED`, `SERVICE_UNAVAILABLE`). Domain contracts declare their own codes next to their schemas (for example `PERIOD_CLOSED` in WS-07).

#### Inventory and purchasing error statuses (bead `legend-ul4s`)

`InventoryError` and `PurchasingError` codes have one HTTP mapping each, declared next to the codes: `inventoryErrorHttpStatus` and `purchasingErrorHttpStatus` (`Record` over the code union, so a new code without a status fails the typecheck) in `@starter/shared/inventory`. The API answers `{ error: { code, message } }` through the single translator `translateDomainError` (`apps/api/src/services/domain-error-http.shared.ts`); the old `translateInventoryError`, `translateCountError` and `translatePurchasingError` delegate to it. `message` is the fixed Indonesian text from `inventoryErrorMessages` / `purchasingErrorMessages`, never the thrown message (it carries ids and amounts). Exception: stock-count services raise `countError(code, message)` with a message they build themselves (status and code still come from the table); those messages hold the document status only, never ids or amounts. Observable changes made with this table: `PURCHASE_ORDER_LINE_MISMATCH` and `THREE_WAY_MATCH_INVALID_INPUT` 409 to 422 (no API path throws them yet); `INSUFFICIENT_STOCK` through the generic translator 422 to 409 (the `insufficientStock` helper already answered 409). Errors that are not an `InventoryError` or `PurchasingError` pass through unchanged. Rule of thumb: not found 404; state, transition, version, duplicate, limit or stock conflict 409; permission-like (self approval, blind detail) 403; invalid or missing input data 422. Purchasing self-approval stays 409 (shipped, asserted by `purchasing-flow.test.ts`); stock-count self-approval stays 403.

### D-CORE-5 Pagination

New list endpoints use cursor (keyset) pagination: query `cursorPageQuerySchema` (`cursor?`, `limit` 1–100, default 25), response `{ data, meta: { limit, nextCursor } }` (`nextCursor: null` on the last page). The cursor is `encodeCursor([sortKey…, id])`, opaque base64url; a tampered cursor decodes to `RangeError` → `VALIDATION_ERROR`. One limit, `CURSOR_MAX_LENGTH` = 1024 characters, applies to both sides: `encodeCursor` throws instead of emitting a longer cursor, and the query schema rejects one. Sort only on bounded columns (timestamps, ids, names up to 150 characters), never free text. Offset paging stays only on the starter Notes example.

### D-CORE-6 Dates

Instants: ISO 8601 with offset (`isoDateTimeSchema`); the server emits UTC with milliseconds (`toIsoDateTime`). Business dates: `YYYY-MM-DD` (`businessDateSchema`), derived on the server; supported range 0001-01-01 to 9999-12-31 (zero-padded year), anything else or an invalid `Date` throws `RangeError`. Times of day: `HH:mm` (`timeOfDaySchema`). Time zone: IANA per outlet, default `Asia/Jakarta`. DB: `TIMESTAMPTZ`, `DATE`, `TIME`.

### D-CORE-7 Business day cutoff (owner Q39, bead `legend-0n8z`)

Each outlet sets `businessDayCutoff` (`outlets.business_day_cutoff`, `HH:mm`, `00:00`..`11:59`, default `04:00`; `businessDayCutoffSchema`, DB check `outlets_business_day_cutoff_check`). On `Outlet`, `createOutletInputSchema` (default `04:00`), `updateOutletInputSchema` (optional; a change is audited as `outlet.business_day_cutoff.updated`) and `outletRefSchema` (defaults to `04:00` when an older producer omits it).

- **Rule.** The business date of an instant is the local calendar date of (instant − cutoff) in the outlet time zone, compared on the local wall clock: with `04:00` in WIB, 23:59 on 2 Nov → 2 Nov, 00:30 / 03:59 on 3 Nov → 2 Nov, 04:00 on 3 Nov → 3 Nov (same in WITA/WIT).
- **One helper** (`@starter/shared/core`, `time.ts`): `businessDateOf(instant, clock)` with `clock: BusinessDayClock = { timeZone, cutoff }` (required — no implicit midnight), `businessDayRange(date, clock) → { start, end }` half-open instants (`[cutoff on date, cutoff on date+1)`; SQL filters use `>= start AND < end`), `addBusinessDays(date, n)` (calendar arithmetic), `DEFAULT_BUSINESS_DAY_CLOCK` (Jakarta, `04:00`) for screens/fixtures without an outlet. API services build the clock with `outletBusinessDayClock(outletRow)` (`apps/api/src/services/outlet-clock.ts`).
- **Uses the business date:** menu price list in force + daily-limit counters + guest/QR menu and its tax rules (`menu-pricing`, `guest-menu`, callers of `reserveMenuItemDailyLimit` pass `businessDateOf(at, clock)`), promo engine price-list day and the min-spend facility reward expiry (`endOfBusinessDay` = next cutoff), tax/service-charge "not before today" (`tax.service`; tenant-wide versions use the default clock), stock-card `fromDate`/`toDate` (`businessDayRange`), facility subscription max-per-day (`sessionsOnBusinessDate`), and on the web: tax, menu, accounting, inventory and kitchen-report "today" defaults and the loyalty reward validity editor (a validity day runs from the cutoff to one second before the next cutoff). Contracts not yet backed by a service (POS EOD `businessDate`, cashier `shiftDate`, dashboards/metrics `metricDate`/`dataThrough`, tax report periods, accounting event `entryDate`) must be produced with `businessDateOf` and the outlet clock.
- **Stays wall-clock** (`localDateOf(instant, timeZone)`, plain local calendar date): opening hours, menu availability schedules, promo time windows (`outletLocalClock`), notification quiet hours, reservation day, HRIS shift roster/attendance day, facility slot day. Promo/voucher validity (`startsAt`/`endsAt`, `validFrom`/`validUntil`) are instants, not dates. Payment settlement periods are bank-supplied dates.
- Tests: `tests/core-contract.test.mjs` "Q39 …" (23:59 / 00:30 / 03:59 / 04:00 × WIB/WITA/WIT, ranges, DST, bounds); API tests named `Q39` in `platform-org-api`, `inventory`, `crm-promo-engine`.

## Migrations: foreign keys into FORCE RLS tables (bead `legend-m007`)

Tenant tables (`employees`, `positions`, `stations`, `outlets`, `chart_of_accounts`, …) use `FORCE ROW LEVEL SECURITY`, so the tenant policy also applies to their owner. The migrator is allowed to be a plain table owner (no SUPERUSER, no BYPASSRLS). Production uses a dedicated migrator login with BYPASSRLS (`legend-jtnd`), and migrations 0000-0064 still need BYPASSRLS on a fresh database; migrations 0065 and later must not depend on it. `ALTER TABLE child ADD CONSTRAINT … FOREIGN KEY … REFERENCES forced_parent` validates under the parent's policy; with no `app.tenant_id` it raises `tenant context is required` and aborts the migration transaction. Even an empty new child table fails.

A new migration that references a FORCE RLS table must use one of these, in this order of preference:

1. **Foreign key inside `CREATE TABLE`** of the new (empty) table: no validation scan runs. When drizzle generates a separate `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY`, move the clause into the `CREATE TABLE` by hand before committing the SQL (keep the constraint name so the drizzle snapshot still matches).
2. **Lift FORCE for the transaction** on every FORCE table the statement touches: `ALTER TABLE public.<table> NO FORCE ROW LEVEL SECURITY;` at the top, `ALTER TABLE public.<table> FORCE ROW LEVEL SECURITY;` after the last statement that needs it, before the file ends (drizzle runs all pending migrations in one transaction, so no other session sees the lifted state). The foreign key validation scan reads both sides as the migrator, so lift the parent and also the child when the child is itself a FORCE table, whatever the row count: a FORCE child fails even when the parent has no RLS (for example `tenants`). Also lift any FORCE table the migration reads or writes (a backfill `INSERT` hits `WITH CHECK`). Examples: `0065_edge_received_events.sql`, `0068_closed_tiger_shark.sql`, `0088_complex_newton_destine.sql` (lifts the existing children `pos_order_tenders`, `pos_order_voids`, `pos_order_refunds`). Restore FORCE on every table you lifted.

```sql
-- Pattern 1: new empty table, foreign key inline (no validation scan).
CREATE TABLE "leave_requests" (
  "tenant_id" uuid NOT NULL,
  "id" uuid NOT NULL,
  "employee_id" uuid NOT NULL,
  CONSTRAINT "leave_requests_pk" PRIMARY KEY ("tenant_id", "id"),
  CONSTRAINT "leave_requests_employee_fk" FOREIGN KEY ("tenant_id", "employee_id")
    REFERENCES "public"."employees" ("tenant_id", "id")
);
--> statement-breakpoint
SELECT app.enforce_tenant_rls('public.leave_requests');

-- Pattern 2: ALTER … ADD FOREIGN KEY on an existing table.
-- Lift the parent and, when it is a FORCE table too, the child.
ALTER TABLE public.employees NO FORCE ROW LEVEL SECURITY;
--> statement-breakpoint
ALTER TABLE public.attendance_logs NO FORCE ROW LEVEL SECURITY;
--> statement-breakpoint
ALTER TABLE "attendance_logs" ADD CONSTRAINT "attendance_logs_employee_fk"
  FOREIGN KEY ("tenant_id", "employee_id") REFERENCES "public"."employees" ("tenant_id", "id");
--> statement-breakpoint
ALTER TABLE public.attendance_logs FORCE ROW LEVEL SECURITY;
--> statement-breakpoint
ALTER TABLE public.employees FORCE ROW LEVEL SECURITY;
```

With both sides lifted, pattern 2 validates every existing child row against the whole parent (all tenants), which is the check we want. Lifting only the parent fails on a FORCE child (`tenant context is required`); setting a dummy `app.tenant_id` instead would hide rows on both sides and either reject a populated child or validate nothing. `ALTER TABLE … NO FORCE` takes an ACCESS EXCLUSIVE lock on each lifted table, held until the whole pending batch commits (restoring FORCE early does not release it), so every read of that table waits for the rest of the migration run. Production's migrator has BYPASSRLS, so there the lift changes nothing but the lock; keep migrations that lift large hot tables (`outlets`, `employees`) short.

Do not use `NOT VALID` (the constraint stays unvalidated forever, and a later `VALIDATE CONSTRAINT` hits the same error) and do not rely on BYPASSRLS for migrations 0065 and later.

Tests: `apps/api/src/test/migration-fk-force-rls.test.ts` reproduces the failure and pins both patterns on a scratch database. `edge-received-events-migration.test.ts` ("applies the full migration folder as the non-superuser owner") applies the real folder from 0065 as a plain owner, so a new migration that breaks the rule fails there; `migrator-role.test.ts` is the contrast case (a plain owner is expected to fail on 0000-0064). `migration-force-rls-guard.test.ts` catches the silent failures: a `NO FORCE` with no later `FORCE` on the same table in the same file, a foreign key `NOT VALID` or a `DISABLE ROW LEVEL SECURITY` in migrations 0065 and later, and (after all migrations) any public table with RLS enabled but not forced other than the three documented ENABLE-only tables `tenant_domains`, `payment_link_tokens` and `delivery_store_index`. Review checklist: any `ADD CONSTRAINT … FOREIGN KEY` in a new migration → check the referenced table for FORCE and the pattern above. Also: any migration that updates `fiscal_periods.status` (a close, reopen, or backfill) fires `app.bump_ledger_version()` (0270), which updates `legal_entities`; `legal_entities` is a FORCE table, so lift FORCE on it (and on `fiscal_periods`) for that migration and restore it afterwards.

## Migrations: a tighter lock_timeout is restored to the saved value (bead `legend-76azz`)

The migrator sets its own `lock_timeout` for the session (`MIGRATION_LOCK_TIMEOUT`, `apps/api/src/db/migration-session.ts`, `legend-jluo`), and drizzle runs every pending file in one transaction. A migration that tightens `lock_timeout` for one statement (for example `'5s'` before `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` on a hot table) must save the value it found with `current_setting('lock_timeout')` and put it back with `set_config('lock_timeout', <saved>, true)` before the file ends. `SET LOCAL lock_timeout TO DEFAULT` (or `= DEFAULT`) and `RESET lock_timeout` restore the role/database default instead, often `0` (wait forever), for every later file in the batch, so a later blocked `ALTER` hangs the deploy and queues POS traffic behind it.

- One `DO` block (preferred, `0143_edc_pan_scrub_separators.sql`): `prior_lock_timeout text := current_setting('lock_timeout')`, then `PERFORM set_config('lock_timeout', '5s', true)`, the statements, and `PERFORM set_config('lock_timeout', prior_lock_timeout, true)`.
- A file split by `--> statement-breakpoint` (`0135_edc_pan_scrub.sql`): save into a transaction-local setting named after the file, `set_config('legend.lock_timeout_before_<NNNN>', current_setting('lock_timeout'), true)`, and restore with `SELECT set_config('lock_timeout', COALESCE(NULLIF(current_setting('legend.lock_timeout_before_<NNNN>', true), ''), current_setting('lock_timeout')), true)` (the fallback keeps a statement-by-statement autocommit run from failing on an empty saved value).
- Never pass `NULL` as the value: `set_config('lock_timeout', NULL, …)` also resets to the server default, and a bare `current_setting(<name>, true)` is `NULL` when the saved setting is missing. Wrap it as above.

Tests: `migration-lock-timeout.test.ts` ("legend-76azz migrations restore the migrator's lock_timeout") fails on any `lock_timeout TO DEFAULT`, `= DEFAULT`, `RESET lock_timeout`, `RESET ALL`, or `set_config('lock_timeout', NULL | current_setting(…, true), …)` in `apps/api/drizzle/*.sql`; `edc-pan-scrub-migration.test.ts` checks that 0135 ("0135 restores the migrator's lock_timeout, not the server default") and 0143 (the NOSUPERUSER NOBYPASSRLS owner case) leave `lock_timeout` as they found it.

## Naming

## Events, outbox and sync (`@starter/shared/events`, bead `legend-m59`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/events`. Tests: `tests/events-contract.test.mjs`. PRD §5 Sinkronisasi, §6 `order_events` / `sync_cursors`.

- **One catalog, typed payloads.** Every event name is listed once in `events/catalog.ts` (`<aggregate>.<past_verb>`, `payloadSchemaRef` = `<name>.v<version>`, derived and enforced). A workstream registers its payload from `<domain>/events.ts` with `defineDomainEvent({ name, payload })`: it throws at module load for a name that is not catalogued or a mismatching version, and returns `envelopeSchema` validating name, version, schema ref and payload together. Adding an event is a one-line catalog change in the owning bead; changing a payload shape means a new `version` and a new ref.
- **Envelope.** Payload is JSON only (`z.json()`): no `Date`, `bigint`, `NaN` or `undefined`, so a row survives JSONB and the edge link unchanged. `actor.type` is `user | ai | mcp_client | device | system`, the same kinds as audit (`mcp` was renamed `mcp_client`); every actor id is a UUID. `deviceId` (nullable, default `null`) is the originating device, as in PRD `order_events.device_id`.
- **Idempotency and order.** `idempotencyKey` is unique per tenant (`eventDedupeKey`). Order is the per tenant + aggregate `sequence` (starts at 1, no gaps): consumers call `classifyEventSequence(lastApplied, event)` and apply only `apply`, drop `duplicate`, and park `gap` while requesting the missing range. Never order by arrival time or ULID.
- **Outbox.** Statuses `pending | processing | delivered | failed`. `attempts` counts leases (a leased or delivered row has at least one). After the worker's retry limit a row becomes terminal `failed` with `lastError` (PRD "retry terbatas"); `isOutboxRowClaimable(row, now)` is the single claim rule (due `pending`, or `processing` with an expired lease). The retry limit and backoff are worker configuration, not contract.
- **Order events by channel** (coordinator decision, legend-6li review): `order.placed` is the QR-channel event owned by WS-03 (`@starter/shared/qr-order`); `order.submitted`, `order.paid`, `order.voided` and `order.refunded` are owned by WS-04 (POS). Consumers that need every new order subscribe to both `order.placed` and `order.submitted`.
- **Adapter events** (`provider_webhook.received`, `wa_inbound_message.received`, `outbound_message.sent|failed`, `edc_transaction.created|settled|cancelled`, `wifi_session.authorized|revoked`, `lock_credential.issued|revoked`, `delivery_channel.action_executed`) are owned by WS-00 in the catalog (`adapterEventNames`). The service wrapping a provider emits them; providers never do. A webhook that fails verification has no trusted tenant and is logged in `gateway_webhook_events`, not published.

## Audit (`@starter/shared/audit`, bead `legend-pnj`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/audit`. Tests: `tests/audit-contract.test.mjs`. PRD §6 `audit_logs`, retention two years, support access (§4).

- **Actor rules.** `user`, `ai`, `mcp_client` need `actorId`; `system` has none; `device` acts as itself (`deviceId === actorId`).

## Adapters (`@starter/shared/adapters`, bead `legend-4lk`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/adapters`. Tests: `tests/adapters-contract.test.mjs`. PRD §5 adapters, §7; provider choices in [providers.md](providers.md).

- **Context.** Every method takes a server-minted `ScopedTenantContext` (D-CORE-3) and the request carries `tenantId`/`outletId` that must equal it; they never widen it. `outletId: null` (storage, email, push, LLM) means tenant-level and needs a tenant-wide `OutletScope`.
- **Idempotent mutations.** Repeating a request returns the first result and has no second side effect; the same key or reference with a different request fails `IDEMPOTENCY_KEY_REUSED` (409). Keys: payments and refunds by `(tenant, idempotencyKey)` (core `idempotencyKeySchema`), everything else by `(tenant, outlet, reference)`. Fakes enforce this, so tests written against them hold for real adapters.
- **`PaymentProvider`** has `createPayment`, `getPayment` (source of truth for scheduled status checks) and `refund` (paid only, up to the paid amount). Statuses follow PRD §5: `pending → paid | expired | failed → refunded`, plus `cancelled`. **`LockProvider`** has `issue` and `revoke`. Fakes expose `simulate(ref, "paid" | "failed" | "expired")` for the provider's asynchronous outcome.
- **WhatsApp / KirimDev (AUTH-02, owner-approved).** `MessagingProvider.verifyWebhook` replaces Meta's `X-Hub-Signature-256` with KirimDev's `X-Kirim-Signature: t=<unix>,v1=<hex>` = HMAC-SHA256(secret, `"<t>." + raw bytes`), rejected when `|now − t| > 300 s`, one `v1` per active secret during rotation (any match passes), compared in constant time via Web Crypto. Every failure is `CoreError` `UNAUTHORIZED` with one message (no oracle). Verify the exact bytes (`express.raw`), before parsing or tenant routing. The dedupe key is the message id (`messages[].id` in the body, not `X-Kirim-Event-Id`, because one signed delivery can carry several messages): the service routes by receiving number, then `receive()` returns `duplicate: true` for a repeated id, and a duplicate or forged message never creates a session. `signKirimWebhook` builds valid headers for route tests. `InboundMessage` no longer carries a header name; WhatsApp numbers are digits (`628…`), text is at most 4096 characters. Source: docs.kirimdev.com/webhooks/signing (1 Nov 2026); recheck it at integration, with live forgery, replay and rotation tests.
- **Outbound safety.** Push endpoints and the tenant-configured LLM `baseUrl` must be public `https` DNS names (no IP literals, credentials, `localhost`, `.local`, `.internal`); the real adapter must also refuse private DNS answers at connect time (rebinding). Email subjects are single-line. Storage keys are relative portable paths without `.` or `..` segments; the real adapter prefixes `tenant/outlet`. `redactLlmConfig` is the only form of an LLM config that may be logged. Lock credentials (door codes) are secrets: never logged, audited or put in an event payload.
- **Not in the contract.** DOIT's `PayBridge-Signature` verifier (header format not yet confirmed) belongs to the WS-05 DOIT adapter.

## Typed web client & idempotency headers (bead `legend-8tv6`)

Code: `apps/web/src/lib/api/endpoint-core.ts`, `apps/web/src/lib/api/client.ts`. Tests: `tests/api-client.test.mjs`, `tests/legend-8tv6-mock.test.mjs`.

Some API writes take their retry identity from an `Idempotency-Key` request header instead of the body, so their strict body contracts stay unchanged. This is the case for the five payment-admin configuration mutations: routing (`PUT`), EDC terminal create (`POST`) and update (`PATCH`), cashier default (`PUT`), and reconciliation resolve (`POST`). Callers pass it per call: `callEndpoint(endpoint, input, { headers: { "Idempotency-Key": key } })`. Features use the `useAttemptKey` pattern: the same payload keeps its key across retries of one user attempt, while a changed payload or a successful save starts a new attempt with a new key. Mock handlers for header-based mutations require the header and replay the first result, failing `IDEMPOTENCY_KEY_REUSED` on a changed request. ## Facility & WFC (`@starter/shared/facility`, bead `legend-lmmn`, reviewed in `legend-cyu.7`)

Code: `packages/shared/src/facility`. Tests: `tests/facility-contract.test.mjs`. PRD §3 F22/F39, §6 K, FAC-01..14, D37/D38.

- **Slots (FAC-02, FAC-06).** A slot is `startsAt → endsAt → cleaningEndsAt`; the unit is occupied on the half-open `tstzrange(startsAt, cleaningEndsAt, '[)')` (`slotRangeLiteral` is the only builder), so back-to-back bookings touch without overlapping. The database backstop is a **partial** exclusion constraint `EXCLUDE USING gist (tenant_id WITH =, unit_id WITH =, slot WITH &&) WHERE (SLOT_HOLD_PREDICATE_SQL)`: cancelled, refunded and no-show tickets release the slot without rewriting their stored range. Only `available` units are bookable, checked in the same transaction.
- **Door credentials (FAC-01, FAC-03).** A credential opens one unit inside `[startsAt − grace, endsAt)` and is verified offline by the lock/edge from its stored window; revocation is the only online action and an unrevoked credential still fails closed at `validUntil`. QR/PIN plaintext goes to the guest once at issue; `qr_hash`/`pin_hash` live only in `accessTicketCredentialDigestSchema` (server/edge) and are keyed digests (HMAC-SHA-256, per-tenant secret), never returned to a client, logged or put in an event.

Issued only after the source transaction is paid (except tier benefit and staff issue); a refund appends `cancel`. Redemption: ticket ↔ `redeem` row is 1:1 (two unique indexes); concurrent redemptions are serialised per (tenant, customer, facility) with an advisory transaction lock, then the balance is recomputed (skipping grants past `expiresAt`) before the insert.
- **Wi-Fi (FAC-12..14, owner rule).** Daily quota = free minutes (peak or off-peak, policy row) + tier bonus + 60 min per **full** Rp30.000 of paid same-day spend (Rp90.000 → +3 h), recomputed from the day's total so an order never counts twice, capped at 1440 minutes. The refresh endpoint (`POST /api/wifi/sessions/current/refresh`) has a strict empty body: the API derives same-day spend from the account's settled payments, so a guest can never raise their own quota. Max 2 devices per account; re-authorising an active device does not count against the limit. When the quota runs out the session drops to the base speed tier, never disconnected. Every number is a `wifi_policies` row.

## POS (`@starter/shared/pos`, bead `legend-4yp`, WS-04)

Code: `packages/shared/src/pos`. Tests: `tests/pos-contract.test.mjs`. Acceptance at contract level: POS-03, POS-04, POS-06 (plus the POS-02/POS-07 vocabulary the screens and documents need).

- **Orders (POS-04).** `posOrderStatusSchema` is §6 exactly (`draft → awaiting_payment → sent → completed`, `voided` on the way). `POS_ORDER_TRANSITIONS` is the single table: completed and voided are terminal, there is no delete operation, and `assertPosOrderMutable` is what every mutating service calls first. A completed sale is corrected by a **linked record**: `posVoidSchema` (keeps the receipt number) or `posRefundSchema` (lines allocated back over the original tender methods by `refundAllocation`, sum exact via core `allocateIdr`, bounded by `assertRefundWithinPaid`). `assertCorrectionTargetsFinalOrder` refuses a correction on anything but a completed sale. Voiding a _non-final_ order is the `void` transition, with reason, note and verified approval on the order row.
- **Money never comes from the client.** `createPosOrder` sends menu ids, quantities, modifiers and notes; `addPosTender` sends the cash **received** (`receivedIdr`) and no amount (`planCashTender` applies `min(received, remaining)` and derives change); a discount sends a rate or a promo/voucher code, never an amount (`applyPosDiscount`); the blind count sends denominations, never expected/counted/variance (`closePosShiftInputSchema` is strict, so a submitted system figure is a validation error). `costSnapshotIdr` (HPP) is server-computed like kitchen's `order_issues.cost_idr`.

The API re-checks the approval server-side; the id alone is not proof. Standard reason vocabularies are proposed in the same shape as F41 ("alasan baku") because the PRD lists them only for remake/comp.
- **Shift and blind count (POS-03).** `pos_shift` aggregates cash sales/refunds/in/out/drops; `shiftExpectedCashIdr` is the only drawer formula. `closeShift(shift, counts, approval, …)` is the whole close as a pure transition: refuse a second close, derive the total from denominations (blind count — the cashier never inputs the system figure), compute variance, require a written note for any difference (U9), require supervisor approval, and produce a row the schema then locks: a closed shift cannot carry edited expected/counted/variance values. Cash moves (`cash_in`, `cash_out`, `drop`) only while the shift is open and always with a reason.
- **Receipts (POS-06).** One `receipt_sequences` row per (outlet, device) with its own prefix (`CLB-P1`); `nextReceiptNumber` increments the device's own run, so offline numbering stays gapless and prefixes keep two terminals unique in the outlet. `assertGaplessReceipts` proves ordinals 1..lastNumber each exist once and match the prefix, voided rows included; `receiptGaps` is what stops a day close; `mergeDeviceReceiptSequence` accepts an idempotent replay, moves the cloud row forward, and refuses a device that would reuse a number. A void never returns an ordinal: the receipt row flips to `voided` with its number.

Deliveries are print/link/email; WhatsApp is excluded on purpose (it costs money, PRD §3 F8). The e-receipt link is returned once and stored hashed.

- **End of day.** `endOfDayRecapSchema` is the F8 "Tutup Hari" report: per-device sales, voids (paid sales corrected), refunds, cash variance, tender rows (`captured − refunded = net`), channel rows and the accounting-sync marker, with the contract-level POS-05 identity `Σ net = sales − refunds − paid voids`. ## Identity & access (`@starter/shared/identity`, bead `legend-7sz`)

Code: `packages/shared/src/identity`. Tests: `tests/identity-contract.test.mjs`. PRD §3 F6/F7, §6 B, flow §4 C and R, AUTH-01..07.

- **Login challenge (AUTH-01).** One row per attempt (§6 `login_challenges`), global like §6 but tenant-scoped by the receiving number or the domain; `tenantId`/`brandId` are null for a platform (Super Admin) login. The WhatsApp code is 8 Crockford symbols (no I/L/O/U) = 40 bits, typed relaxed (`O`→`0`, `I`/`L`→`1`, separators ignored), shown once, valid 5 minutes, single use, and bound to the browser that asked (`browser_binding_hash`). The email magic link is valid 15 minutes (PRD silent; 119connect window) and deliberately **not** browser-bound — the guest clicks it in whichever browser the mail app opens, so the one-time token is the proof. The Google challenge is bound by its OAuth state (10 minutes, PRD silent). The WhatsApp code completes in the KirimDev webhook (no browser), so its binding is enforced when the polling browser collects the session, once (`assertLoginChallengeSessionClaimable`); Google checks its state binding at the callback. Codes come from `generateLoginCode` (Web Crypto, `byte & 31` over the 32-symbol alphabet), never `Math.random`. Only keyed digests are stored (`identityDigestSchema`, HMAC-SHA-256 hex); every WhatsApp number is normalized by `normalizeWhatsAppNumber` (`0812…`/`+62…` → `62812…`) and digested by `whatsAppNumberDigest` — reservations' `hashGuestContact` is that same function, so rows link across modules; a plaintext code, token, binding, session token, TOTP secret or pin never reaches a wire DTO, log, audit row or event.
- **Inbound WhatsApp (AUTH-02, owner rule).** Signature (`X-Kirim-Signature` HMAC) and message-id dedupe live in the adapters contract. Identity's half: only a pending, unexpired, correctly bound challenge completes, and it completes exactly once (`completeLoginChallenge`); a duplicate or forged message therefore never creates a second session. Login is by reverse OTP: the system sends no WhatsApp message (AUTH-03); the guest sends the filled-in message, the browser polls its challenge and gets the session.
- **Rate limits (AUTH-04).** At most 5 open challenges per device or IP in 15 minutes and 10 login messages per number per hour; both throw core `RATE_LIMITED`.
- **Replies (AUTH-03).** Off by default (`WHATSAPP_LOGIN_REPLY_ENABLED_DEFAULT = false`). If a tenant enables replies, `recordLoginReply` sends while the provider's free monthly quota lasts and stops at the cap, without blocking the browser confirmation.

Statuses `pending | approved | rejected | expired | cancelled`; the approver is never the requester (`APPROVER_IS_REQUESTER`), and the deadline sweep expires the row and blocks the action (fail closed). AI and MCP sources carry the human they act for in `requestedBy`.

A source module calls `openApprovalRequest(tx, context, { sourceModule, actionType, objectType, objectId, amountIdr, outletId, requestedBy, source, requestReason, payload?, idempotencyKey? })` **inside its own transaction** after authorising the action itself, and stores the returned `chainId` on its own pending row; `{ required: false }` means the amount is below every tier (proceed), `APPROVAL_POLICY_MISSING` means nobody may approve (stay blocked). ## Reservations, delivery channels & public website (bead `legend-m7ak`)

Code: `packages/shared/src/reservation`, `.../delivery`, `.../website` (subpaths `@starter/shared/reservation`, `/delivery`, `/website`). Tests: `tests/reservation-contract.test.mjs`, `tests/delivery-contract.test.mjs`, `tests/website-contract.test.mjs`. PRD v1.7 §3 F19/F20/F21 (the bead's "F22-F24" labels are stale), §3.22-24, §6.G `reservations` / `waitlist_entries` / `delivery_channel_orders`, RSV-01..03, D12.

- **Table slots (RSV-01).** A reservation holds each table on the half-open `tstzrange(reservedFor, reservedFor + durationMinutes, '[)')`; `reservationRangeLiteral` is the only builder and `reservationTableSlotsOverlap` the only overlap rule, so back-to-back reservations do not conflict. The BE bead stores slot rows in a join table with an exclusion constraint (BREAKDOWN W30); a cancelled/no-show slot keeps its history with `releasedAt` set and stops blocking.
- **DP (RSV-02).** The DP is collected through a WS-05 bill link, not an intent opened at booking: booking opens a link for the DP amount alone (no tax, service charge or table label; reference `RSV-<id>`; created by the system actor `system:reservation`) and returns its `/bayar/<token>` path once (sealed for idempotent replay); the guest creates the intent on the hosted page. `depositPaymentId` is the SETTLED intent on that link and stays null until one is paid. `depositStatus` is derived from WS-05, never stored: the settled intent's status once `depositPaymentId` is set; `pending` while the DP is awaited (or `expired` once the link's window passed); null when no DP applies or nothing was paid before the reservation closed. `pending_deposit` is the only state with an unpaid DP and always carries the DP amount and a `depositStatus`; `confirmed`/`seated`/`completed` with a required DP need `paid`, `partially_refunded` or `refunded`. The DP amount is the snapshot's `depositAmountIdr` (required) or 0/that amount (optional). `payment.paid` of an intent on a reservation's link confirms it (worker consumer, idempotent, decided under the reservation row lock); a `pending_deposit` hold whose link expired unpaid (or that never got a link within the snapshot payment window) is released as `cancelled` (`deposit_not_paid`) by the worker sweep and lazily on booking. A DP paid after its reservation closed is recorded and refunded in full. Seating emits `reservation.seated` with `depositAllocatedIdr`, the DP allocated to the opened table session (`reservation_deposit_allocations`); the session is opened through WS-03 `openStaffSeatedSession` (every table locked in id order; secondary tables freed when the session closes). DP refunds (RSV-03 split, late DP) are WS-05 refund requests filed by `system:reservation` (`refund_status` `pending` → `requested` with `refund_payment_refund_id`; retried with backoff up to 8 attempts, then audited for a human); the approval stays WS-05's (`payment.reconcile`, never the requester). WS-05 `refundView.requestedBy` is a user id or a `systemRefundActorSchema` literal, with a display name fallback (`Sistem (reservasi)`).
- **Policy snapshot (RSV-03).** The outlet policy is frozen into `reservations.policy_snapshot` at creation (`version`, deposit requirement/amount, payment window, free-cancellation hours, late/no-show refund basis points, private-room minimum spend). `cancellationDepositOutcome` / `noShowDepositOutcome` read only that snapshot and report its version; refund basis points use the core money helpers with an explicit rounding mode.
- **Waitlist (§3.22).** `waiting → called → seated | left`, `waiting/called → cancelled`; `contactHash` is the only contact data stored or returned. `estimatedWaitMinutes` is a bounded server quote (`clampWaitEstimate`), never queue math on the client.
- **Event pre-order (§3.22).** A package is `pricePerPaxIdr` + per-person item composition + `leadTimeHours`; a pre-order snapshots package name, price per pax and composition, so `subtotalIdr = pax × pricePerPaxIdr` (net of tax and service; owner decision 12). It becomes a WS-04 order with channel `reservation` on the event day.
- **Delivery channels (§3.23, F20, D12).** `delivery_channel_orders` keeps `externalOrderId` unique per platform, the reported `grossIdr`/`commissionIdr`, the platform payload's `payloadHash` and `source` (`platform` adapter vs `manual_pos`). The fulfilment machine `received → accepted → preparing → ready → picked_up → delivered` (plus `cancelled`/`rejected`) maps every step to a WS-00 `DeliveryChannel` action via `deliveryActionForTransition`. A mapped line carries our `channelPriceIdr`; a different platform price is `price_mismatch` for staff review, an unknown item is `unmatched` and blocks KDS injection (an order with an unmatched line has no `orderId`). `net = gross − commission` is derived (`deliveryNetIdr`), never stored twice; `reconcileDeliveryLine` classifies statement lines as `matched` / `variance` / `unknown_order`.
- **Public website (§3.24, F21).** `publicSiteSchema` (brand, outlet, hours, location/geo, hero/gallery with alt text, highlights, featured menu with prices, promos, contact, GBP link, SEO meta) and `publicMenuPageSchema` (sections, items, availability) are public DTOs with no internal ids beyond menu ids. `pricesExcludeTaxAndService: true` is a literal on both pages (owner decision 12). `buildRestaurantJsonLd` / `buildMenuJsonLd` produce schema.org `Restaurant` / `Menu`; `serializeJsonLd` escapes `<` and U+2028/U+2029 for the SSR script block; `sitemapEntriesFor` covers `/`, `/menu`, `/reservation` only (`/member` is a sign-in page robots.txt disallows).
- **Routes.** Public (tenant from the host): `GET /api/public/outlets/:outletId/reservation-availability`, `POST .../reservations`, `GET .../reservation-packages`, `POST .../waitlist`, `GET /api/public/site`, `/api/public/site/menu`. Staff (outlet session + RBAC): reservations list/detail/table assignment/seat/cancel/no-show/preorder, package list, waitlist list/call/resolve, delivery channel state/sync, delivery order list/detail/manual/status, reconciliation.
- **Events (WS-08 catalog line).** `reservation.created|confirmed|seated|completed|cancelled|no_show`, `waitlist_entry.called|seated|left`, `reservation_preorder.placed`, `delivery_order.received|status_changed|settled`. Payloads carry ids, states and money; no guest name or phone hash, and `refund + forfeit` must equal the paid DP.
- **PRD-silent decisions.** Guest contact is write-only (`contactPhone` in, `contactHash` out); `contactHash` is `hashGuestContact(phone, secret)` = HMAC-SHA-256 with a server secret (at least 16 characters), never a bare SHA-256 (phone numbers are enumerable). Reservation timestamps in the DTO (`seatedAt`, `completedAt`, `closedAt`, `closeReason`) are derived from events, not stored columns. The delivery order's status is the channel fulfilment state that drives platform actions; `orders.status` stays WS-04's. Platform-reported gross/commission are recorded as reported (they are external money, not our price list), so the usual "server computes money" rule applies to the pre-order and to manual POS entry only.
- **Idempotency and abuse limits (legend-t8bz, legend-5jqa).** Every reservation mutation (public booking, table assignment, seat, cancel, no-show) requires the `Idempotency-Key` request header (8-100 characters, core `idempotencyKeySchema`); a missing or malformed header is `VALIDATION_ERROR` (422). The key is never read from the body: the body goes to the strict contract parse untouched, so a body `idempotencyKey` is refused as an unknown key. A replay with the same key returns the stored result; the same key with a different request fingerprint fails `IDEMPOTENCY_KEY_REUSED` (409). Precedent: payment-admin and approval routes. The public booking POST has its own write limiter, separate from the public-read limiter: per client IP and per tenant per minute (defaults 10 and 60, `PUBLIC_WRITE_PER_IP` / `PUBLIC_WRITE_PER_TENANT`), plus a cap of 5 per guest contact, tenant and outlet per hour. The contact bucket key is the keyed WhatsApp digest (never the raw number) in a bounded in-memory map; a replay of an `Idempotency-Key` already seen for that contact is not charged to the contact cap again. Over the limit: 429 `RATE_LIMITED` with `Retry-After`. The availability GET stays on the read limiter. Counters are per API process.

## Payroll (`@starter/shared/hris/payroll`, bead `legend-zjwa`)

Code: `packages/shared/src/hris/payroll`. Tests: `tests/payroll-contract.test.mjs`. PRD v1.7 §3 Kelompok D 30–31, §4 Alur K, §6 H payroll tables, R20, PAYR-01..05.

- **Statutory tables are data.** `statutory_rates` rows are versions of one of `bpjs_kes jht jkk jkm jp ptkp pph21_ter pph21_annual overtime thr` (last three added: annual Pasal 17 recalculation, versioned overtime formula per PAYR-02, THR tenure rule). Lifecycle mirrors the tax engine: `draft → published` (immutable, `effectiveFrom ≥ today`) or `archived`. The version in force is the latest published `effectiveFrom ≤ date`; none → `PAYROLL_STATUTORY_TABLE_NOT_FOUND`, same date twice → `…_AMBIGUOUS`. No regulation number lives in code; fixtures are labelled `ILUSTRASI`.
- **Rates in basis points, amounts in whole rupiah.** Every computation (`computeBpjsContribution`, `computeTerWithholding`, `computeProgressiveTax`, `computeOvertimePay`, `computeThr`) rounds once with the table's `RoundingMode`. BPJS base = wage clamped to `[floor, cap]`; JKK rate per employer risk class. TER: PTKP status → category (table data) → monthly gross bracket, inclusive upper bound.
- **Run state machine (PAYR-01).** `draft → simulated (repeatable) → hr_approved → approved → locked → paid | reversed`; `return_to_draft` from simulated/hr_approved/approved clears approvals. `simulate` has no side effect (`PAYROLL_RUN_SIDE_EFFECTS.simulate = []`); lock needs both approvals by two people; reversal (PAYR-05) only from `locked`, requested then decided by someone else. A paid run is not reversed (corrected in a later run).
- **Frozen runs (PAYR-02).** From `locked` the run is frozen; `statutoryVersionsForRun` returns the versions pinned in `config_snapshot` by id (missing/changed → `PAYROLL_SNAPSHOT_MISMATCH`); open runs resolve by pay date.
- **Payslip arithmetic.** Schemas refuse a payslip or run total that does not add up: gross = Σ earnings, deductions = Σ deductions, net = gross − deductions ≥ 0, deductions = BPJS employee + PPh 21 withheld + kasbon + other, net = bank transfer + cash. Each line's `kind` must follow its component category, so no earning can masquerade as a deduction (or a reimbursement as one). `assertBankFileMatchesRun` (PAYR-04) checks the file rows against the bank-paid payslips.
- **Kasbon.** `planLoanDeductions` never deducts more than net pay or `maxDeductionOfNetPayBp` of it; the shortfall is carried. Deducted only at lock; reversal restores it.
- **Privacy (HR-03).** Payslips, employee pay components and run totals are payroll-role data; the PWA list has no amounts until the 6-digit payslip PIN (POST body). `bankTransferRowSchema` holds the decrypted account number and lives only in the server-only subpath `@starter/shared/hris/payroll/server` (never the client-safe barrel, which refuses to export it). Events carry run totals (journal) but no per-employee salary.

### Payslip PIN (bead `legend-2ap3`)

Routes `routes/hris-payslip.routes.ts`, services `payslip-pin.service.ts` and `hris-payslip.service.ts`, migration `0257_payslip_pins`.

- **One PIN per employee** (`payslip_pins`): 6 digits, scrypt over a tenant-pepper HMAC bound to the `payslip` domain + tenant + employee, so a staff device pin hash never verifies as a payslip PIN. Never stored, logged, audited or put in an idempotency response.
- **Attempts.** Same rules as the staff pin: 5 misses lock for 15 minutes; the fifth miss already answers `PAYSLIP_PIN_LOCKED` (423); a locked PIN is refused without checking the guess; a correct PIN clears the counter. The counter commits before the error. `PAYSLIP_PIN_NOT_SET` (409) before a PIN exists; wrong PIN `PAYSLIP_PIN_INVALID` (403).
- **View** (`POST /me/payslips/:id/view`): own employee only (another employee's, another tenant's and a missing payslip are all 404, no attempt counted). Sets `viewed_at` once and audits `payslip.viewed` (sensitive). The same idempotency key replays the outcome without a second attempt; the decrypted payslip is never stored.
- **Set / change** (`PUT /me/payslip-pin`): first set needs no `currentPin`; a change needs it and a wrong one counts as an attempt.
- **HR reset** (`POST /employees/:employeeId/payslip-pin/reset`, `payroll.run`, reason required): deletes the hash and lock and voids open codes; HR never sees or sets the PIN.
- **WhatsApp reset** (`POST /me/payslip-pin/reset-otp`, `/verify`): 6-digit code, 5 min, 5 tries, single use, keyed hash only, sent through the port `PayslipPinOtpSender` to the employee's verified WhatsApp identity. No sender or no number: 503 `SERVICE_UNAVAILABLE`. Unknown, expired and used codes answer 403 like a wrong code.
- **Audit:** `payslip_pin.set|changed|reset|locked|otp_requested|otp_reset`, `payslip.viewed`; ids, status and lock time only.

- **Events.** `payroll.locked`, `payroll.approval_requested`, `payroll.paid`, `payroll.reversed`, `payslip.created`, `employee_loan.disbursed`, `reimbursement.paid`. The WS-07 posting rule still listens to the placeholder `payroll_run.completed`; switching it to `payroll.locked` (+ reversal) is a follow-up.
