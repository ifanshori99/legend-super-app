# Contract conventions (WS-00 core)

Bead `legend-6gu` · PRD v1.7 §3 "Kontrak Bersama", §6 conventions, TEN-02/TEN-03, ORD-06.
Code: `packages/shared/src/core` (import `@starter/shared/core`). Tests: `tests/core-contract.test.mjs` (runtime) and `packages/shared/src/core/type-tests.ts` (compile time).

Every domain contract (`CT` bead) builds on these rules. Change them only through a WS-00 bead.

## Decisions

### D-CORE-1 Ids: UUID everywhere, ULID for time-ordered aggregates, one `uuid` column type

PRD §6 says all ids are UUID, but operational events use ULID, and several ULID primary keys (orders, order_items, kitchen tickets, stock_ledger, access tickets) are referenced by UUID-typed foreign keys (for example `order_items.order_id`, `stock_ledger.source_id`).

- **Postgres:** every id column, primary or foreign, is `uuid`. A ULID is 128 bits, so it is stored losslessly in a `uuid` column (`ulidToUuid` / `uuidToUlid`). Byte order equals time order, so index locality and ordering are kept. This keeps every §6 foreign-key type as written.
- **Wire and TypeScript:** one id type per aggregate everywhere it appears. UUID aggregates use `uuidIdSchema<"XId">()`; ULID aggregates use `ulidIdSchema<"XId">()` and always travel as the 26-character ULID text, including in foreign-key fields of other aggregates (for example `payment.orderId`). The API converts at the DB boundary (a Drizzle custom type in the BE schema bead).
- **Generation:** UUIDs come from Postgres `gen_random_uuid()` or `crypto.randomUUID()`. ULIDs come from `createUlidFactory()` (monotonic within a millisecond, so one device's outbox stays ordered offline) or `createUlid()`.
- Ids are branded per aggregate (`TenantId`, `OutletId`, …), so mixing them is a type error.

### D-CORE-2 Money: BIGINT whole rupiah for amounts, NUMERIC(14,4) only per-unit cost and quantity

PRD §6 says money is BIGINT rupiah, but `stock_ledger.unit_cost_idr` and `recipes.theoretical_cost_idr` are NUMERIC(14,4) and `ai_jobs.cost_idr` is NUMERIC(12,2). Tech-lead decision:

- **Any amount that is posted, paid, billed, allocated or reported** (order totals, payments, journals, payroll, profit share, budgets, stock value totals): `BIGINT` whole rupiah. TypeScript/JSON: `Idr`, a branded safe integer (JSON `number`; every realistic amount is far below 2^53). Field suffix `Idr` (`totalIdr` ↔ `total_idr`).
- **Per-unit cost and quantity** (`stock_ledger.quantity`, `stock_ledger.unit_cost_idr`, `recipes.theoretical_cost_idr`, yields, UOM factors): `NUMERIC(14,4)`. TypeScript/JSON: `Decimal4`, a decimal string such as `"0.0180"` (the form `pg` returns), computed as scaled bigint, never as a float.
- **`ai_jobs.cost_idr`** (per-call estimate, fractions of a rupiah): `NUMERIC(14,4)` instead of NUMERIC(12,2), so there is one decimal type. Totals derived from it for reports or quotas are rounded to `Idr`.
- Converting between the two is always explicit and rounded: `extendCostIdr(quantity, unitCost, mode)`, `unitCostOf(totalIdr, quantity, mode)`.
- **Rounding is explicit.** Every helper that can produce a fraction takes a `RoundingMode` (`half_up` = half away from zero, `half_even`, `down`, `floor`, `ceil`). Which mode and cash increment a tenant uses is configuration (PRD F11 "aturan pembulatan", WS-05 tax contract), not code. `roundToIncrement` returns the rounded amount and the rounding line (`orders.rounding_idr`).
- **Splits sum exactly (ORD-06).** `allocateIdr(total, weights)` / `splitIdrEvenly` use the largest-remainder method with deterministic index tie-breaks; use them for split bills, combo revenue allocation, service-charge pools and profit share (weights in basis points, 10,000 = 100%).

### D-CORE-3 Tenant from domain or token, never from the client (TEN-02)

- **Provenance is enforced at runtime, not only by types.** `TenantContext` and `OutletScope` are valid only if the server minted them: an internal WeakSet registry (`core/trust.ts`, exported from no entry point) records every minted object. Plain objects, JSON round-trips, `structuredClone` and spread copies are never members.
- **Minting is server-only.** `@starter/shared/core/server` exports `establishTenantContext({ tenantId, brandId, source })` (`source` in `domain | session | device | mcp_token | job | webhook`), `establishOutletScope(tenant, assignment)` and `establishScopedTenantContext(tenant, assignment)`. It throws at import time where a DOM exists, and the browser-safe `@starter/shared/core` exports only the checks. Import the server entry only from `apps/api` and the edge runtime, with values the server resolved itself (host name → `tenant_domains`, verified token, job row, receiving webhook account; outlet reach from verified role assignments, which the RBAC contract `legend-0mc` expands from brand or station level to outlet ids).
- **Service boundaries assert.** Services take `ScopedTenantContext` (or `TenantContext`) and call `assertTrustedScopedContext` / `assertTrustedTenantContext` first, never accept a bare `tenantId` from the request. An `OutletScope` is bound to its tenant; pairing it with another tenant's context fails.
- Request schemas are built with `clientInputSchema({...})`: declaring `tenantId` / `tenant_id` is a compile error and throws at module load; parsing is strict, so a submitted `tenantId` is rejected.
- The database enforces the same with RLS and `SET LOCAL` (bead `legend-73d`). `login_challenges` and `wa_inbound_messages` resolve the tenant from the receiving WhatsApp number (`source: "webhook"`) and are service-scoped without RLS (coordinator decision).
- **TEN-03.** `isOutletInScope(scope, outletId)` and `assertOutletInScope` are the single check; an untrusted scope throws `TypeError` (fail closed). Lists, reports, exports, Tanya AI and MCP derive their outlet filter with `outletIdsForQuery(scope, requested?)`: nothing requested → the whole scope (`{ kind: "all" }` or the assigned outlets); any requested outlet outside the scope → `CoreError` `OUTLET_OUT_OF_SCOPE` (403).
- Ids normalize on parse (UUID lowercase, ULID uppercase), so comparisons are plain `===`.
- Two copies of the shared package in one process would not trust each other's objects (fails closed). Keep `@starter/shared` a single workspace dependency.

### D-CORE-4 Errors

Envelope: `{ "error": { "code", "message", "details"?: [{ field, message }], "requestId"? } }`, the starter's shape. `code` is stable `UPPER_SNAKE_CASE`; the UI maps it to catalog text. `message` is a safe Indonesian fallback. Core codes and their HTTP status live in `coreErrorHttpStatus` (starter codes plus `TENANT_CONTEXT_REQUIRED`, `OUTLET_OUT_OF_SCOPE`, `FEATURE_DISABLED`, `CONFLICT`, `IDEMPOTENCY_KEY_REUSED`, `PRECONDITION_FAILED`, `RATE_LIMITED`, `SERVICE_UNAVAILABLE`). Domain contracts declare their own codes next to their schemas (for example `PERIOD_CLOSED` in WS-07).

### D-CORE-5 Pagination

New list endpoints use cursor (keyset) pagination: query `cursorPageQuerySchema` (`cursor?`, `limit` 1–100, default 25), response `{ data, meta: { limit, nextCursor } }` (`nextCursor: null` on the last page). The cursor is `encodeCursor([sortKey…, id])`, opaque base64url; a tampered cursor decodes to `RangeError` → `VALIDATION_ERROR`. One limit, `CURSOR_MAX_LENGTH` = 1024 characters, applies to both sides: `encodeCursor` throws instead of emitting a longer cursor, and the query schema rejects one. Sort only on bounded columns (timestamps, ids, names up to 150 characters), never free text. Offset paging stays only on the starter Notes example.

### D-CORE-6 Dates

Instants: ISO 8601 with offset (`isoDateTimeSchema`); the server emits UTC with milliseconds (`toIsoDateTime`). Business dates: `YYYY-MM-DD` in the outlet time zone (`businessDateSchema`, `businessDateOf(instant, outlet.timeZone)`), derived on the server; supported range 0001-01-01 to 9999-12-31 (zero-padded year), anything else or an invalid `Date` throws `RangeError`. Times of day: `HH:mm` (`timeOfDaySchema`). Time zone: IANA per outlet, default `Asia/Jakarta`. DB: `TIMESTAMPTZ`, `DATE`, `TIME`.

## Naming

- DB: English `snake_case` tables, columns and status values (PRD §6). Wire/TypeScript: `camelCase` keys, same English words (`total_idr` → `totalIdr`, `tenant_id` → `tenantId`). Status values stay `snake_case` strings on the wire (`awaiting_payment`).
- Schema names end in `Schema`; inferred types drop it (`orderSchema` → `Order`). Request schemas are `create…Schema`, `update…Schema`, `list…QuerySchema`, built with `clientInputSchema`.
- Domain events: `<aggregate>.<past_verb>` (`order.paid`), catalogued in the WS-00 event contract (`legend-m59`). Core defines no events; event ids are ULIDs.

## Domain contract folder layout

```
packages/shared/src/<domain>/      # e.g. pos, payments, inventory (English, kebab-case)
  schemas.ts      # zod schemas + inferred types (DTOs and request inputs)
  events.ts       # event payload schemas, registered in the WS-00 catalog
  errors.ts       # domain error codes (optional)
  fixtures.ts     # Cafe Legend mock data; must parse against schemas.ts
  index.ts        # public surface
```

- One `package.json` export per domain: `"./<domain>": "./src/<domain>/index.ts"`. Import from the subpath, never deep paths.
- Import shared conventions only from `@starter/shared/core` (inside the package: relative `../core`).
- No Node-only or browser-only APIs (no `Buffer`, `node:*`, `window`, `document`); the code runs in the API, the web app and the edge. Keep files loadable by native Node ESM with type stripping (the edge runtime and the contract tests load them without a bundler or resolve hook): relative imports carry the `.ts` extension (`./ids.ts`; `allowImportingTsExtensions` is on in `tsconfig.base.json`), type-only imports use `import type`, and no `enum`, `namespace` or constructor parameter properties.
- Every contract bead adds a fixture test (fixtures parse) to `tests/<domain>-contract.test.mjs`.

## Events, outbox and sync (`@starter/shared/events`, bead `legend-m59`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/events`. Tests: `tests/events-contract.test.mjs`. PRD §5 Sinkronisasi, §6 `order_events` / `sync_cursors`.

- **One catalog, typed payloads.** Every event name is listed once in `events/catalog.ts` (`<aggregate>.<past_verb>`, `payloadSchemaRef` = `<name>.v<version>`, derived and enforced). A workstream registers its payload from `<domain>/events.ts` with `defineDomainEvent({ name, payload })`: it throws at module load for a name that is not catalogued or a mismatching version, and returns `envelopeSchema` validating name, version, schema ref and payload together. Adding an event is a one-line catalog change in the owning bead; changing a payload shape means a new `version` and a new ref.
- **Envelope.** Payload is JSON only (`z.json()`): no `Date`, `bigint`, `NaN` or `undefined`, so a row survives JSONB and the edge link unchanged. `actor.type` is `user | ai | mcp_client | device | system`, the same kinds as audit (`mcp` was renamed `mcp_client`); every actor id is a UUID. `deviceId` (nullable, default `null`) is the originating device, as in PRD `order_events.device_id`.
- **Idempotency and order.** `idempotencyKey` is unique per tenant (`eventDedupeKey`). Order is the per tenant + aggregate `sequence` (starts at 1, no gaps): consumers call `classifyEventSequence(lastApplied, event)` and apply only `apply`, drop `duplicate`, and park `gap` while requesting the missing range. Never order by arrival time or ULID.
- **Outbox.** Statuses `pending | processing | delivered | failed`. `attempts` counts leases (a leased or delivered row has at least one). After the worker's retry limit a row becomes terminal `failed` with `lastError` (PRD "retry terbatas"); `isOutboxRowClaimable(row, now)` is the single claim rule (due `pending`, or `processing` with an expired lease). The retry limit and backoff are worker configuration, not contract.
- **Order events by channel** (coordinator decision, legend-6li review): `order.placed` is the QR-channel event owned by WS-03 (`@starter/shared/qr-order`); `order.submitted`, `order.paid`, `order.voided` and `order.refunded` are owned by WS-04 (POS). Consumers that need every new order subscribe to both `order.placed` and `order.submitted`.
- **Adapter events** (`provider_webhook.received`, `wa_inbound_message.received`, `outbound_message.sent|failed`, `edc_transaction.created|settled|cancelled`, `wifi_session.authorized|revoked`, `lock_credential.issued|revoked`, `delivery_channel.action_executed`) are owned by WS-00 in the catalog (`adapterEventNames`). The service wrapping a provider emits them; providers never do. A webhook that fails verification has no trusted tenant and is logged in `gateway_webhook_events`, not published.

## Audit (`@starter/shared/audit`, bead `legend-pnj`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/audit`. Tests: `tests/audit-contract.test.mjs`. PRD §6 `audit_logs`, retention two years, support access (§4).

- **Actor rules.** `user`, `ai`, `mcp_client` need `actorId`; `system` has none; `device` acts as itself (`deviceId === actorId`).
- **Sensitive access needs a reason** (`sensitiveAccess: true` requires a non-blank `reason`; PRD support access).
- **`action`** is dotted lowercase (`role.updated`), **`objectType`** one snake_case word (`menu_item`).
- **Masking.** Use `maskAuditChanges(value, safeFields)` for `before` and `after`; the schema rejects any sensitive-named field that does not hold `[REDACTED]` (`auditChangesAreMasked`) and a `maskedChanges` over 64 KiB. The deny list (`isSensitiveAuditKey`) always beats the safe list: long terms match as fragments (`bank_account`, `apiKey`, `alamat`, `nohp`), short ones (`pin`, `pan`, `otp`, `nik`, `ktp`, `hp`, `ip`, `dob`, `cvv`) only as whole words, so `pinCode` is redacted but `shipping` and `company` are not. Safe scalar arrays are kept, `null` stays `null`. Free text is never safe: leave it off the safe list.
- **`ipHash`** is `await hashIpForAudit(ip, secret)`: HMAC-SHA256 with a server secret (at least 16 characters), never a bare hash (the IPv4 space is enumerable).
- Append-only is enforced by the database bead; the schema cannot.

## Adapters (`@starter/shared/adapters`, bead `legend-4lk`, reviewed in `legend-cyu.4`)

Code: `packages/shared/src/adapters`. Tests: `tests/adapters-contract.test.mjs`. PRD §5 adapters, §7; provider choices in [providers.md](providers.md).

- **Context.** Every method takes a server-minted `ScopedTenantContext` (D-CORE-3) and the request carries `tenantId`/`outletId` that must equal it; they never widen it. `outletId: null` (storage, email, push, LLM) means tenant-level and needs a tenant-wide `OutletScope`.
- **Idempotent mutations.** Repeating a request returns the first result and has no second side effect; the same key or reference with a different request fails `IDEMPOTENCY_KEY_REUSED` (409). Keys: payments and refunds by `(tenant, idempotencyKey)` (core `idempotencyKeySchema`), everything else by `(tenant, outlet, reference)`. Fakes enforce this, so tests written against them hold for real adapters.
- **`PaymentProvider`** has `createPayment`, `getPayment` (source of truth for scheduled status checks) and `refund` (paid only, up to the paid amount). Statuses follow PRD §5: `pending → paid | expired | failed → refunded`, plus `cancelled`. **`LockProvider`** has `issue` and `revoke`. Fakes expose `simulate(ref, "paid" | "failed" | "expired")` for the provider's asynchronous outcome.
- **WhatsApp / KirimDev (AUTH-02, owner-approved).** `MessagingProvider.verifyWebhook` replaces Meta's `X-Hub-Signature-256` with KirimDev's `X-Kirim-Signature: t=<unix>,v1=<hex>` = HMAC-SHA256(secret, `"<t>." + raw bytes`), rejected when `|now − t| > 300 s`, one `v1` per active secret during rotation (any match passes), compared in constant time via Web Crypto. Every failure is `CoreError` `UNAUTHORIZED` with one message (no oracle). Verify the exact bytes (`express.raw`), before parsing or tenant routing. `X-Kirim-Event-Id` is the dedupe key: the service routes by receiving number, then `receive()` returns `duplicate: true` for a repeated id, and a duplicate or forged message never creates a session. `signKirimWebhook` builds valid headers for route tests. `InboundMessage` no longer carries a header name; WhatsApp numbers are digits (`628…`), text is at most 4096 characters. Source: docs.kirimdev.com/webhooks/signing (1 Nov 2026); recheck it at integration, with live forgery, replay and rotation tests.
- **Outbound safety.** Push endpoints and the tenant-configured LLM `baseUrl` must be public `https` DNS names (no IP literals, credentials, `localhost`, `.local`, `.internal`); the real adapter must also refuse private DNS answers at connect time (rebinding). Email subjects are single-line. Storage keys are relative portable paths without `.` or `..` segments; the real adapter prefixes `tenant/outlet`. `redactLlmConfig` is the only form of an LLM config that may be logged. Lock credentials (door codes) are secrets: never logged, audited or put in an event payload.
- **Not in the contract.** DOIT's `PayBridge-Signature` verifier (header format not yet confirmed) belongs to the WS-05 DOIT adapter.

## Facility & WFC (`@starter/shared/facility`, bead `legend-lmmn`, reviewed in `legend-cyu.7`)

Code: `packages/shared/src/facility`. Tests: `tests/facility-contract.test.mjs`. PRD §3 F22/F39, §6 K, FAC-01..14, D37/D38.

- **Slots (FAC-02, FAC-06).** A slot is `startsAt → endsAt → cleaningEndsAt`; the unit is occupied on the half-open `tstzrange(startsAt, cleaningEndsAt, '[)')` (`slotRangeLiteral` is the only builder), so back-to-back bookings touch without overlapping. The database backstop is a **partial** exclusion constraint `EXCLUDE USING gist (tenant_id WITH =, unit_id WITH =, slot WITH &&) WHERE (SLOT_HOLD_PREDICATE_SQL)`: cancelled, refunded and no-show tickets release the slot without rewriting their stored range. Only `available` units are bookable, checked in the same transaction.
- **Door credentials (FAC-01, FAC-03).** A credential opens one unit inside `[startsAt − grace, endsAt)` and is verified offline by the lock/edge from its stored window; revocation is the only online action and an unrevoked credential still fails closed at `validUntil`. QR/PIN plaintext goes to the guest once at issue; `qr_hash`/`pin_hash` live only in `accessTicketCredentialDigestSchema` (server/edge) and are keyed digests (HMAC-SHA-256, per-tenant secret), never returned to a client, logged or put in an event.
- **Entitlements (FAC-04, FAC-05).** Append-only ledger `grant + / redeem − / cancel − / expire −`; balance = sum, negative throws. Issued only after the source transaction is paid (except tier benefit and staff issue); a refund appends `cancel`. Redemption: ticket ↔ `redeem` row is 1:1 (two unique indexes); concurrent redemptions are serialised per (tenant, customer, facility) with an advisory transaction lock, then the balance is recomputed (skipping grants past `expiresAt`) before the insert.
- **Wi-Fi (FAC-12..14, owner rule).** Daily quota = free minutes (peak or off-peak, policy row) + tier bonus + 60 min per **full** Rp30.000 of paid same-day spend (Rp90.000 → +3 h), recomputed from the day's total so an order never counts twice, capped at 1440 minutes. Max 2 devices per account; re-authorising an active device does not count against the limit. When the quota runs out the session drops to the base speed tier, never disconnected. Every number is a `wifi_policies` row.
- **Events (WS-09 catalog line, all via `defineDomainEvent`).** Bead names map to catalog names: ticket issued/redeemed → `access_ticket.issued|redeemed`; unit needs cleaning → `cleaning_task.created`; entitlement issued/expired/revoked → `facility_entitlement.issued|expired|revoked`; Wi-Fi quota changed → `wifi_quota.updated`; plus `access_event.recorded`, `facility_session.started|ended`, `subscription.billed`, `facility_incident.raised`. Payloads carry ids only — no credential, digest, device fingerprint or personal data. Device authorisation itself is the WS-00 adapter event `wifi_session.authorized|revoked`.

## POS (`@starter/shared/pos`, bead `legend-4yp`, WS-04)

Code: `packages/shared/src/pos`. Tests: `tests/pos-contract.test.mjs`. PRD v1.7 §3 F8 "POS Kasir & Captain Order", F43/F44, §4 E "Alur Kasir Membuka dan Menutup Shift", §5 "Model event untuk operasional", §6.C (`orders`, `order_items`, `order_events`, `receipt_sequences`, `pos_shifts`, `cash_movements`). Acceptance at contract level: POS-03, POS-04, POS-06 (plus the POS-02/POS-07 vocabulary the screens and documents need).

- **Orders (POS-04).** `posOrderStatusSchema` is §6 exactly (`draft → awaiting_payment → sent → completed`, `voided` on the way). `POS_ORDER_TRANSITIONS` is the single table: completed and voided are terminal, there is no delete operation, and `assertPosOrderMutable` is what every mutating service calls first. A completed sale is corrected by a **linked record**: `posVoidSchema` (keeps the receipt number) or `posRefundSchema` (lines allocated back over the original tender methods by `refundAllocation`, sum exact via core `allocateIdr`, bounded by `assertRefundWithinPaid`). `assertCorrectionTargetsFinalOrder` refuses a correction on anything but a completed sale. Voiding a _non-final_ order is the `void` transition, with reason, note and verified approval on the order row.
- **Money never comes from the client.** `createPosOrder` sends menu ids, quantities, modifiers and notes; `addPosTender` sends the cash **received** (`receivedIdr`) and no amount (`planCashTender` applies `min(received, remaining)` and derives change); a discount sends a rate or a promo/voucher code, never an amount (`applyPosDiscount`); the blind count sends denominations, never expected/counted/variance (`closePosShiftInputSchema` is strict, so a submitted system figure is a validation error). `costSnapshotIdr` (HPP) is server-computed like kitchen's `order_issues.cost_idr`.
- **Tenders and accounting.** `POS_TENDER_METHODS` is cash, qris, va, ewallet, card, edc_card, edc_qris, points. A voucher is a **discount line** (as in the QR quote), never a tender, so every captured tender maps to a bucket (`cash | gateway | edc | points`) and `order.paid` carries exactly the amount keys the merged WS-07 posting rule reads (`paidCashIdr`, `paidGatewayIdr`, `paidEdcIdr`, `paidPointsIdr`, `discountIdr`, `grossSalesIdr`, `serviceChargeIdr`, `pbjtIdr`, `roundingIdr`). `order.refunded` carries the refund keys. A bucket that disagrees with the tender lines is rejected at the contract, so a sale cannot post an unbalanced journal. Payment confirmation stays WS-05 (verified webhook / EDC); a tender is `authorized` until then, and only `captured` money counts.
- **POS-02 approvals.** Every void and refund carries `approvedBy` + `approvalRequestId` (WS-01 `approval_requests`, §3.7 action types `void`/`refund`); a manual discount above the outlet's `discountApprovalThresholdBp` needs one too (`requiresDiscountApproval`, strict "above", promo/member discounts excluded because their configuration is the approval). The API re-checks the approval server-side; the id alone is not proof. Standard reason vocabularies are proposed in the same shape as F41 ("alasan baku") because the PRD lists them only for remake/comp.
- **Shift and blind count (POS-03).** `pos_shift` aggregates cash sales/refunds/in/out/drops; `shiftExpectedCashIdr` is the only drawer formula. `closeShift(shift, counts, approval, …)` is the whole close as a pure transition: refuse a second close, derive the total from denominations (blind count — the cashier never inputs the system figure), compute variance, require a written note for any difference (U9), require supervisor approval, and produce a row the schema then locks: a closed shift cannot carry edited expected/counted/variance values. Cash moves (`cash_in`, `cash_out`, `drop`) only while the shift is open and always with a reason.
- **Receipts (POS-06).** One `receipt_sequences` row per (outlet, device) with its own prefix (`CLB-P1`); `nextReceiptNumber` increments the device's own run, so offline numbering stays gapless and prefixes keep two terminals unique in the outlet. `assertGaplessReceipts` proves ordinals 1..lastNumber each exist once and match the prefix, voided rows included; `receiptGaps` is what stops a day close; `mergeDeviceReceiptSequence` accepts an idempotent replay, moves the cloud row forward, and refuses a device that would reuse a number. A void never returns an ordinal: the receipt row flips to `voided` with its number.
- **Documents (POS-07).** `receiptDocumentSchema` (receipt/kuitansi) always carries the outlet name and address (D40), item lines, service charge, at least one tax line and the payment methods, and its totals must equal the order's. `invoiceDocumentSchema` adds who is billed (NPWP optional) and a due date for corporate/event orders. Deliveries are print/link/email; WhatsApp is excluded on purpose (it costs money, PRD §3 F8). The e-receipt link is returned once and stored hashed.
- **Hold & fire.** Items start `held` with no `firedAt`; `fireStatus` and `firedAt` always agree; `firePosOrderItems` takes explicit items or one course (never both). `sent`/`completed` orders record `firedAt`.
- **End of day.** `endOfDayRecapSchema` is the F8 "Tutup Hari" report: per-device sales, voids (paid sales corrected), refunds, cash variance, tender rows (`captured − refunded = net`), channel rows and the accounting-sync marker, with the contract-level POS-05 identity `Σ net = sales − refunds − paid voids`. Stock deduction is a flag because the PRD makes it optional ("bila dipilih").
- **Events (WS-04 catalog line).** `order.submitted`, `order.paid`, `order.voided`, `order.refunded` (the four the catalog already reserved for WS-04), `cashier_shift.opened`, `cashier_shift.closed`, plus two names this bead added: `day.closed` and `cash_movement.recorded`. All via `defineDomainEvent`; `order_events` rows (`posOrderEventSchema`) are the append-only sync log (§5) with a per-order sequence.
- **Not in the contract.** Server pricing/tax computation (WS-05 tax contract, same path as the QR quote), payment capture (WS-05/EDC adapters), stock deduction (WS-06), approval inbox mechanics (WS-01), loyalty point valuation (WS-08). Endpoint handlers and RLS are the WS-04 BE beads (`legend-kk7`, `legend-…`), and the screens are the WS-04 FE beads.
## QR order guest read models (`@starter/shared/qr-order`, `guest.ts`, beads `legend-2m4`/`legend-8sh`/`legend-woz`/`legend-tz1`)

The customer screens of `/t/[token]` need read models the WS-03 contract beads (`legend-6li`, `legend-j85`) did not define. They live in `qr-order/guest.ts` with fixtures and are served by the FE mock until the backend bead (`legend-4jm`) implements and ratifies them:

- `getQrMenu` `GET /api/qr/menu/:qrToken` (public, SSR): items with the channel price **excluding tax and service charge** (owner rule), variants (absolute price), modifier groups with min/max, labels, allergens, `photoUrl` (null until the media library has one), sold-out state, zone payment mode, zone hours (`orderingOpen`) and the tax/service rates for the price note.
- `getMenuSuggestions` (AI-01): server-applied rules (margin, stock, hours); only orderable items.
- `listSessionOrderIssues`: guest-safe failed-item view (no cost, no staff names); swap options carry a server-computed `differenceIdr` (ORD-03), voucher credit carries `valueIdr`. The guest never sees a refund (ORD-08).
- `createGuestPayment` / `getGuestPayment`: target is one order (pay-first), one split share, or the whole bill; methods `qris`, `ewallet`; the client sends no amount; `paid` only from the verified gateway callback (ORD-02).
- `getPointClaim` / `claimSessionPoints`: per-person point claim, 24 h after settlement; `requiresLogin` for anonymous guests.
- `getOrderEtas`: per-order estimate from WS-04 pacing for the status screen (ORD-11 keeps the pre-checkout estimate in the quote).

## Identity & access (`@starter/shared/identity`, bead `legend-7sz`)

Code: `packages/shared/src/identity`. Tests: `tests/identity-contract.test.mjs`. PRD §3 F6/F7, §6 B, flow §4 C and R, AUTH-01..07.

- **Login challenge (AUTH-01).** One row per attempt (§6 `login_challenges`), global like §6 but tenant-scoped by the receiving number or the domain; `tenantId`/`brandId` are null for a platform (Super Admin) login. The WhatsApp code is 8 Crockford symbols (no I/L/O/U) = 40 bits, typed relaxed (`O`→`0`, `I`/`L`→`1`, separators ignored), shown once, valid 5 minutes, single use, and bound to the browser that asked (`browser_binding_hash`). The email magic link is valid 15 minutes (PRD silent; 119connect window) and deliberately **not** browser-bound — the guest clicks it in whichever browser the mail app opens, so the one-time token is the proof. The Google challenge is bound by its OAuth state (10 minutes, PRD silent). The WhatsApp code completes in the KirimDev webhook (no browser), so its binding is enforced when the polling browser collects the session, once (`assertLoginChallengeSessionClaimable`); Google checks its state binding at the callback. Codes come from `generateLoginCode` (Web Crypto, `byte & 31` over the 32-symbol alphabet), never `Math.random`. Only keyed digests are stored (`identityDigestSchema`, HMAC-SHA-256 hex); every WhatsApp number is normalized by `normalizeWhatsAppNumber` (`0812…`/`+62…` → `62812…`) and digested by `whatsAppNumberDigest` — reservations' `hashGuestContact` is that same function, so rows link across modules; a plaintext code, token, binding, session token, TOTP secret or pin never reaches a wire DTO, log, audit row or event.
- **Inbound WhatsApp (AUTH-02, owner rule).** Signature (`X-Kirim-Signature` HMAC) and message-id dedupe live in the adapters contract. Identity's half: only a pending, unexpired, correctly bound challenge completes, and it completes exactly once (`completeLoginChallenge`); a duplicate or forged message therefore never creates a second session. Login is by reverse OTP: the system sends no WhatsApp message (AUTH-03); the guest sends the filled-in message, the browser polls its challenge and gets the session.
- **Rate limits (AUTH-04).** At most 5 open challenges per device or IP in 15 minutes and 10 login messages per number per hour; both throw core `RATE_LIMITED`.
- **Replies (AUTH-03).** Off by default (`WHATSAPP_LOGIN_REPLY_ENABLED_DEFAULT = false`). If a tenant enables replies, `recordLoginReply` sends while the provider's free monthly quota lasts and stops at the cap, without blocking the browser confirmation.
- **Identity graph (AUTH-07).** Identities are `whatsapp | email | google` with a unique value digest per type. A verified WhatsApp number is the customer profile key; `assertWhatsAppVerifiedForLoyalty` refuses points without one. Linking a value owned by another account is `IDENTITY_ALREADY_LINKED`; the flow is merge, not link. `planIdentityMerge` keeps the older account (tie: smaller id), moves the other's identities and names the verified WhatsApp identity that proves the merge; orders, points and roles are re-pointed by the service in one transaction.
- **Sessions (AUTH-05, §3 F6).** Server-side, revocable per device. Customer sessions last 90 days (absolute). Management sessions last 30 idle minutes: `expiresAt` is the idle deadline and `recordSessionActivity` pushes it at most once a minute, never shortens it, and ignores background polls; `isSessionIdleWarning` drives the two-minute warning. `sessionGate` returns `revoked | expired | mfa_required | ok`, so an MFA role without a verified factor cannot open a guarded surface; access owns the per-action MFA check. A platform session has `tenantId: null` and is audited by the platform service (no tenant event stream).
- **Staff pin (§3 F6).** `setStaffPinSchema` refuses all-same and straight-run pins (PRD silent). Six digits per user per outlet on a registered device; five misses lock it (`PIN_LOCKED`, 423). PRD names no release, so the lock lasts 15 minutes and a supervisor override (AUTH-06) may clear it at once. Trivial pins (one repeated digit, a straight ascending/descending run) are `WEAK_STAFF_PIN`.
- **Overrides and approval requests (AUTH-06, §3 F7).** `recordApprovalDecision` also refuses an approver who decided an earlier level (`priorApproverIds`, distinct actor) on its own, fail closed. The POS override record stays `access.posOverrideSchema` (requester, approver, reason, value, `approvalRequestId`); this contract adds the generic `approval_requests` row. One row is **one level's decision**, because §6 gives a single `decided_by/decided_at/reason`: a level-2 request opens only after level 1 approves (`nextApprovalLevel`), a rejection or expiry ends the chain. `requestReason` is the requester's justification (AUTH-06 "alasan"), `reason` is the approver's note (F7 "approve/reject with reason"), `amountIdr` is the value the matrix tiered on, `deadlineAt` defaults to `createdAt + 60 min` (PRD asks for a deadline, names no number). Statuses `pending | approved | rejected | expired | cancelled`; the approver is never the requester (`APPROVER_IS_REQUESTER`), and the deadline sweep expires the row and blocks the action (fail closed). AI and MCP sources carry the human they act for in `requestedBy`.
- **Reused, not redefined.** Roles, custom-role inputs, role assignments, `approval_policies`/`upsertApprovalPolicySchema`, the matrix validator and the POS override come from `@starter/shared/access`; the identity fixtures export the access fixture objects themselves.
- **Events (WS-01 line).** `login_challenge.created|completed`, `identity.linked`, `session.created`, `session.revoked`, `approval.requested`, `approval.decided`, all via `defineDomainEvent`; payloads are ids and enums only (no code, digest, token, reason or personal data). This bead added `session.revoked`, `approval.requested` and `approval.decided` to the catalog.
- **Endpoints.** Sign-in (`/api/auth/login-challenges/{whatsapp,email}`, poll/cancel, magic link, Google start/callback), `GET /api/auth/me`, MFA enroll/verify/delete, session list/revoke, staff pin verify/set, approval inbox/create/get/decide and the RBAC admin routes (`/api/access/roles`, `role-assignments`, `approval-policies`). Tenant and outlet never come from a path or body (TEN-02).

## Reservations, delivery channels & public website (bead `legend-m7ak`)

Code: `packages/shared/src/reservation`, `.../delivery`, `.../website` (subpaths `@starter/shared/reservation`, `/delivery`, `/website`). Tests: `tests/reservation-contract.test.mjs`, `tests/delivery-contract.test.mjs`, `tests/website-contract.test.mjs`. PRD v1.7 §3 F19/F20/F21 (the bead's "F22-F24" labels are stale), §3.22-24, §6.G `reservations` / `waitlist_entries` / `delivery_channel_orders`, RSV-01..03, D12.

- **Table slots (RSV-01).** A reservation holds each table on the half-open `tstzrange(reservedFor, reservedFor + durationMinutes, '[)')`; `reservationRangeLiteral` is the only builder and `reservationTableSlotsOverlap` the only overlap rule, so back-to-back reservations do not conflict. The BE bead stores slot rows in a join table with an exclusion constraint (BREAKDOWN W30); a cancelled/no-show slot keeps its history with `releasedAt` set and stops blocking.
- **DP (RSV-02).** `pending_deposit` is the only state with an unpaid DP and always carries `depositPaymentId` + amount; `confirmed` requires a settled required DP (`depositIsSettled`); the DP amount is the snapshot's `depositAmountIdr` (required) or 0/that amount (optional); seating emits `reservation.seated` with `depositAllocatedIdr`, the DP allocated to the opened table session (`table_sessions.reservation_id`). The money itself is WS-05's (`payment_intents.reservation_id`).
- **Policy snapshot (RSV-03).** The outlet policy is frozen into `reservations.policy_snapshot` at creation (`version`, deposit requirement/amount, payment window, free-cancellation hours, late/no-show refund basis points, private-room minimum spend). `cancellationDepositOutcome` / `noShowDepositOutcome` read only that snapshot and report its version; refund basis points use the core money helpers with an explicit rounding mode.
- **Waitlist (§3.22).** `waiting → called → seated | left`, `waiting/called → cancelled`; `contactHash` is the only contact data stored or returned. `estimatedWaitMinutes` is a bounded server quote (`clampWaitEstimate`), never queue math on the client.
- **Event pre-order (§3.22).** A package is `pricePerPaxIdr` + per-person item composition + `leadTimeHours`; a pre-order snapshots package name, price per pax and composition, so `subtotalIdr = pax × pricePerPaxIdr` (net of tax and service; owner decision 12). It becomes a WS-04 order with channel `reservation` on the event day.
- **Delivery channels (§3.23, F20, D12).** `delivery_channel_orders` keeps `externalOrderId` unique per platform, the reported `grossIdr`/`commissionIdr`, the platform payload's `payloadHash` and `source` (`platform` adapter vs `manual_pos`). The fulfilment machine `received → accepted → preparing → ready → picked_up → delivered` (plus `cancelled`/`rejected`) maps every step to a WS-00 `DeliveryChannel` action via `deliveryActionForTransition`. A mapped line carries our `channelPriceIdr`; a different platform price is `price_mismatch` for staff review, an unknown item is `unmatched` and blocks KDS injection (an order with an unmatched line has no `orderId`). `net = gross − commission` is derived (`deliveryNetIdr`), never stored twice; `reconcileDeliveryLine` classifies statement lines as `matched` / `variance` / `unknown_order`.
- **Public website (§3.24, F21).** `publicSiteSchema` (brand, outlet, hours, location/geo, hero/gallery with alt text, highlights, featured menu with prices, promos, contact, GBP link, SEO meta) and `publicMenuPageSchema` (sections, items, availability) are public DTOs with no internal ids beyond menu ids. `pricesExcludeTaxAndService: true` is a literal on both pages (owner decision 12). `buildRestaurantJsonLd` / `buildMenuJsonLd` produce schema.org `Restaurant` / `Menu`; `serializeJsonLd` escapes `<` and U+2028/U+2029 for the SSR script block; `sitemapEntriesFor` covers `/`, `/menu`, `/reservation`, `/member`.
- **Routes.** Public (tenant from the host): `GET /api/public/outlets/:outletId/reservation-availability`, `POST .../reservations`, `GET .../reservation-packages`, `POST .../waitlist`, `GET /api/public/site`, `/api/public/site/menu`. Staff (outlet session + RBAC): reservations list/detail/table assignment/seat/cancel/no-show/preorder, package list, waitlist list/call/resolve, delivery channel state/sync, delivery order list/detail/manual/status, reconciliation.
- **Events (WS-08 catalog line).** `reservation.created|confirmed|seated|completed|cancelled|no_show`, `waitlist_entry.called|seated|left`, `reservation_preorder.placed`, `delivery_order.received|status_changed|settled`. Payloads carry ids, states and money; no guest name or phone hash, and `refund + forfeit` must equal the paid DP.
- **PRD-silent decisions.** Guest contact is write-only (`contactPhone` in, `contactHash` out); `contactHash` is `hashGuestContact(phone, secret)` = HMAC-SHA-256 with a server secret (at least 16 characters), never a bare SHA-256 (phone numbers are enumerable). Reservation timestamps in the DTO (`seatedAt`, `completedAt`, `closedAt`, `closeReason`) are derived from events, not stored columns. The delivery order's status is the channel fulfilment state that drives platform actions; `orders.status` stays WS-04's. Platform-reported gross/commission are recorded as reported (they are external money, not our price list), so the usual "server computes money" rule applies to the pre-order and to manual POS entry only.

## Profit share & dividends (bead `legend-cq2`)

Code: `packages/shared/src/accounting/profit-share*.ts`. Tests: `tests/accounting-contract.test.mjs` (SH-03, SH-04). PRD v1.7 §3.37, §6 I, §4 P.

- **Shares (SH-03).** A share version sums to exactly 10,000 bp before submit and approval; the approver differs from the requester (AUTH-06); a new version's `effectiveFrom` advances past the approved one.
- **Calculation.** Closed periods only. reserve = half-up(net profit × `reserveBp`); gross per shareholder = `allocateIdr` over the allocations sorted by `shareholderId` (largest remainder, ties to the lowest id); tax = half-up(gross × `taxWithholdingBp`), one configurable rate per profit entity for launch (per-shareholder-type rates later). A share too small for Rp1 is `NOTHING_TO_DISTRIBUTE`.
- **Runs (SH-04).** One regular run per profit entity and closed period (hard rule; partial unique index excluding cancelled runs). Approved/paid runs are frozen; a correction is an adjustment run that keeps the corrected run's entity, share version and split (`assertAdjustmentMatchesTarget`).
- **Journal.** `distribution.completed`: debit `retained_earnings` gross (`distributedIdr`), credit `bank` net (`paidNetIdr`), credit `dividend_tax_payable` (CoA 2204 Utang PPh Dividen) the withholding (`taxWithheldIdr`); the payload refuses `distributed ≠ tax + net`.

## Purchasing (bead `legend-ejk`)

Code: `packages/shared/src/inventory/purchasing`. Tests: `tests/purchasing-contract.test.mjs`. PRD v1.7 §3.18, §4 Alur I, §6.E, INV-05.

- **Approvals.** PR, PO and supplier payment approvers differ from the requester/creator (§3.7).
- **Receipts (INV-05).** Only `received − rejected` enters stock and GRNI (at PO unit cost); cumulative accepted quantity per PO line never exceeds the ordered quantity.
- **Supplier invoice money.** `goodsIdr` = invoiced goods at PO price (clears GRNI); `priceVarianceIdr` = invoice price − PO price (to inventory); `totalIdr = goods + variance + services + ppn` is the billed amount; `payableIdr = total − pph23`. The `supplier_invoice.recorded` payload refuses a split that does not balance.

- **Payments.** Only a `matched` invoice is payable; a new payment plus open (`pending_approval`/`approved`) requests may not exceed `outstandingIdr`.
- **Petty purchases.** Deny by default: no configured limit → refused; outlet row overrides the tenant row.
